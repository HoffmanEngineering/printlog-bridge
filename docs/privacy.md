# Privacy and security

What printlog-bridge sends, where it connects, and how it keeps your keys. Each guarantee below is what the code does today, and a test fails if that changes: most are in [`tests/test_privacy.py`](../tests/test_privacy.py), and the others are named where they come up.

## What leaves the printer

The bridge sends 3D Print Log exactly these calls, and nothing else:

| Call | When | What it carries |
| --- | --- | --- |
| `GET /api/Users/me` | `doctor` | nothing; checks the key |
| `GET /api/Printers/{id}` | `doctor`; at start and every 5 minutes; when a print starts and ends | nothing; checks `printer_id`, and reads which spool is loaded in each slot |
| `GET /api/Users/me/user-settings` | first print after a start | nothing; reads your default visibility and comment settings |
| `PUT /api/Connections/{instance}` | at start, then every 5 minutes (the heartbeat) | `kind` (`moonraker`, `bambu` or `prusalink`), `displayName` (`printlog-bridge (<printer name from your config>)`), `agentVersion`, `printerId`, and the printer's health: see [The heartbeat](#the-heartbeat). The answer carries `latestAgentVersion`, the newest bridge release, which 3D Print Log reads from this repository's tags; it is how the bridge hears about an update |
| `GET /api/Prints/claimable` | a print starts (and when a print ends that the bridge saw no start for), unless `adopt_prints = false` | `printerId` and `createdAfter` (the start time less `adopt_window`): looks for a print you made yourself, with the Slic3r uploader, the Cura plugin or by hand, to log the job to instead of a new one. The file name is compared on the bridge, not sent |
| `POST /api/Prints/{id}/claim` | a print starts and one of yours matches it | `externalSource`, `externalId`, `connectionInstanceId` and `startDate`, as for `POST /api/Prints`; your print keeps everything else |
| `POST /api/Prints` | a print starts and there's no print of yours to adopt (never with `create_prints = false`) | `printerId`, `title` (made from the file name), `fileName` (the file's name, without its folder), `startDate`, `status`, `viewStatus` and `allowComments` (your account defaults), `externalSource` (`moonraker`, `bambu` or `prusalink`), `externalId` and `connectionInstanceId` (a random id this bridge made for the printer, plus Moonraker's job id, or for a Bambu printer the job's start time and name, or for a PrusaLink printer its job number and file name), the slicer's estimated print time and filament (length and weight, and the weight per tool on a multi-tool file; for a resin printer, the resin's volume in mL), when the file has them, each tool's row linked to the spool loaded in its slot, and `notes` when the printer's RFID reader disagrees with a spool's material or color |
| `GET /api/Prints/{id}` | a print ends | nothing; reads what you changed in the app |
| `POST /api/Prints/{id}/complete` | a print ends | `status` (the outcome), `endedAt`, `printTimeInSeconds`, and per tool (`slot`) the filament length Klipper fed (linked to the spool you chose in the app; from printers that report weight, the grams instead, and from printers that report only the slicer's estimate, `actualIsEstimate: true`; from a resin printer, the slicer's volume in mL, always marked as an estimate), split into a row per spool when a tool's spool changed mid-print |
| `PATCH /api/Prints/{id}` | a print fails or is cut short, a spool changed mid-print, or a print was paused for a filament change with no spool assigned | `notes`: a line saying why, with Klipper's error message when there is one; which spools a tool changed between, where; how to split a filament change's usage |
| `POST /api/Prints/{id}/image` | a print starts, and when it ends | the slicer's thumbnail (at start), one webcam frame (at end, unless `snapshots = false`) |
| `POST /api/Prints/{id}/slicer-settings` | once per print, after it starts, unless `slicer_settings = false` (and not for a print you made with the Slic3r uploader or the Cura plugin, which has the slicer's own) | `configBlock`: the `; key = value` settings the slicer wrote after the G-code; `header`: the file's first lines, through `; HEADER_BLOCK_END` (PrusaSlicer: its first line), which name the slicer and its version; both scrubbed, see below. `metadata`: what Moonraker read from the file: `slicer`, `slicerVersion`, `layerHeightMm`, `firstLayerHeightMm`, `nozzleDiameterMm`, `filamentName`, `filamentType`, `firstLayerNozzleTemperatureC`, `firstLayerBedTemperatureC` |
| `GET /api/Subscription/me` | moonraker-timelapse renders a print's video (at most once an hour) | nothing; reads whether your account has Pro, which attachments need |
| `GET /api/Prints/{id}/files` | before attaching a video (Pro) | nothing; reads which files the print has, so a video is never attached twice |
| `POST /api/Prints/{id}/files/upload-url` | attaching a video (Pro) | `fileName` (the video's name, `timelapse_<your file's name>_<date>.mp4`), `contentType` (`video/mp4`), `sizeBytes` |
| `POST /api/Prints/{id}/files/confirm` | the video is uploaded (Pro) | `blobPath` (where 3D Print Log said to put it), `fileName`, `contentType`, `sizeBytes` |
| `GET /api/Filaments/by-tag/{uid}` | `PRINTLOG_SET_SPOOL TAG=...`, a Snapmaker U1 reads a spool's RFID tag, or a spool active in your own Spoolman has a tag UID (`nfc_id`) and no material is linked to its Spoolman id | the tag's UID |
| `GET /api/Filaments/by-number/{n}` | a spool is picked in Mainsail, Fluidd or KlipperScreen, or with `SET_ACTIVE_SPOOL`, and Moonraker's `[spoolman]` server is 3D Print Log | the spool number |
| `GET /api/Filaments/by-spoolman-id/{n}` | the active spool, or a tool's spool, changes in your own Spoolman (Moonraker's `[spoolman]` server isn't 3D Print Log) | the spool's id in your Spoolman |
| `PUT /api/Printers/{id}/slots/{slot}` | `PRINTLOG_SET_SPOOL`, a U1 tag that matches one of your spools, or a spool active in your own Spoolman that matches one of your materials | `filamentId` (the spool), `slotLabel` (`T0`, `T1`...) |
| `DELETE /api/Printers/{id}/slots/{slot}` | `PRINTLOG_CLEAR_SPOOL` | nothing |
| `PUT /api/bridges/me` | paired (a device token with `bridge:sync`): at start, every 5 minutes (as 3D Print Log says) and right after a scan | the check-in: `agentVersion`, `mode` (`local` or `remote`), `hostName` (this computer's host name; in Docker, the container's), `networks` (the private /24s it sees: its own and those of the printers it knows), `lastSweepAt` (when it last scanned, as you asked in the app) and `discovered`: see [Discovery and check-in](#discovery-and-check-in). The answer carries the printers you connected to it in the app |
| `GET /api/bridges/me/desired` | paired, every minute (as 3D Print Log says) | nothing but `If-None-Match`; reads the printers you connected to the bridge in the app, and whether you asked for a scan |
| `GET /api/device-grants/pairing` | `pair`, and `run` the first time, with no API key or device token | nothing, not even a credential; reads which sign-in service and app pairing uses (or that pairing is off) |
| `POST /api/device-grants` | pairing, once you approve the bridge | `deviceId` (a random id the bridge made once, kept in `device_id`) and `name` (`printlog-bridge on <this computer's host name>`, or what `--name` or `PRINTLOG_BRIDGE_NAME` says), with the sign-in service's access token as the only credential. The answer is the bridge's device token |
| `GET /api/Printers/summary` | `pair`, and the first run, for a `[printer]` without `printer_id` | nothing; lists your printers to choose from |
| `POST /api/Printers` | `pair`, when you choose to create a printer | `name`, `make`, `model`, `slotCount`, `isActive` and `description`, as you confirmed them. The suggestions come from the printer: Moonraker's host name, Klipper's kinematics and extruder count; a Bambu printer's model, from its serial number; PrusaLink's host name and whether it has an MMU |
| `PUT /api/Printers/{id}` | a spool is assigned to a tool beyond the printer's slot count in 3D Print Log | the printer as 3D Print Log returned it, with only `slotCount` raised to the printer's tool count; not sent when its make, model or name is empty |

Every request also carries one credential, never both: the device token from pairing (`Authorization: Bearer pld_...`) when there is one, otherwise the API key (`X-Api-Key`). And `User-Agent: printlog-bridge/<version>`.

The video itself goes, with Pro, straight to 3D Print Log's file storage (Azure Blob Storage): one `PUT` of the file to the address `upload-url` gave, carrying only the file, its type and size, `x-ms-blob-type` and the `User-Agent`. **Never the API key**, nor anything else from your config. That address holds a signature that lets anyone write the file for 15 minutes, so it is never logged or kept: an error shows it with the signature as `***`.

That is all. In particular:

- **No toolpaths leave the printer, and only two parts of a G-code file are read: its header and its slicer settings.** Moonraker's metadata says where a file's G-code starts and ends, and the bridge reads only what lies outside that, by byte range (`Range: bytes=...` from Moonraker's file API in remote mode, the same ranges from the file in local mode): the start of the file up to where the G-code begins, at most 64 KB, and the end of the file from the line break that ends the G-code's last line, at most its last 512 KB. The first line of that read is always dropped, as it may be cut: Moonraker v0.9.3 and older count where the G-code ends in characters rather than bytes, so after non-ASCII text or CRLF line endings it points into the settings, and half a line could carry part of a key no scrubber recognises. When Moonraker doesn't say where the G-code begins or ends (or says it ends before it begins), it reads the first 4 KB and the last 128 KB, and keeps only the comment and blank lines the file ends with. Of the start it keeps only the comment lines the file begins with, through `; HEADER_BLOCK_END` (PrusaSlicer: its first line), never a G-code line; the thumbnails there are not sent this way. The file is never fetched through a redirect, which would take Moonraker's key elsewhere. It reads only `.gcode`, `.g` and `.gco` files, only once per print, and a file whose size isn't what Moonraker recorded for the job (replaced since) isn't read at all. A server that answers with the whole file instead of the range is hung up on before anything is read.
- **Hosts and credentials are blanked before the settings leave the printer.** A slicer writes how it reaches your printer into every file. In the header and the settings block, the value of every `; key = value` (or `; key: value`) line whose key contains `print_host`, `printhost`, `apikey`, `api_key`, `password`, `passwd`, `token`, `secret`, `user`, `cookie`, `credential`, `authorization`, `access_code` or `post_process` is removed; the key stays, with an empty value. Lines end at every line break Python knows (`\r`, `\n`, `\f`, `\v`, `\x1c`-`\x1e`, U+0085, U+2028, U+2029), and a value runs to where 3D Print Log ends the line, so a file with unusual line endings can't hide a key. 3D Print Log removes the same keys again on its side, and never stores the text itself.
- **An API without the endpoint** (it answers 405 or 501) **is not asked again for 24 hours**: until then no G-code file is read either.
- **`slicer_settings = false` turns it off**, in `[bridge]` for every printer or in a printer's section for that one. Then the G-code file is never asked for, and no slicer settings are sent, not even Moonraker's summary.
- **The thumbnail is read only from a picture.** It is read from the picture Moonraker extracted into `.thumbs/`, and only from a file named as a picture (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.bmp`); anything else is skipped before it is opened. A file that isn't a picture is never sent, whatever its name. The G-code file itself is never uploaded; doing so is a planned opt-in (printlog-bridge#15). The only file ever uploaded whole is moonraker-timelapse's video, below.
- **No folder names or paths.** `fileName` is the file's own name; the folders it sits in on the printer are dropped.
- **No other printer data.** Temperatures, positions, macros, the rest of `printer.cfg` and the rest of Moonraker's history stay on the printer. Of your macros and saved variables the bridge reads only each tool's Spoolman spool (`spool_id` on `gcode_macro T<n>`, `t<n>__spool_id` in `[save_variables]`), and sends 3D Print Log only that id, as below. The bridge also reads Moonraker's config (`server.config`) on each connect and in `doctor`, to find a `[notifier ...]` section that already logs prints to 3D Print Log (printlog-bridge#10). Nothing from it is sent, and the warning names only the section and its file, never its URL, which holds your API key.
- **Moonraker's Spoolman integration is synced both ways only when it's 3D Print Log.** On every connect the bridge reads Moonraker's config, and for this uses only `[spoolman] server` from it, to compare its host with `api_url` (only the host is ever logged, never the address with its secret; the rest of the config isn't kept, logged or traced). When the host matches, it also reads Moonraker's active spool, and sets it to the active tool's spool number.
- **Your own Spoolman is only ever read, through Moonraker.** With a Spoolman server of your own, the bridge reads Moonraker's active spool (and each tool's, when your macros keep them), and the spool's record with `GET /v1/spool/{id}` through Moonraker's Spoolman proxy. It never writes to Spoolman and never sets Moonraker's active spool: Moonraker reports usage to Spoolman already. It connects to your Spoolman server only through Moonraker. Of the spool's record, 3D Print Log is sent its id and the tag UID in its `nfc_id` field, to find the material linked to it; its name, vendor, weights, price, location, lot and comment stay on your network (the name appears in the bridge's own log).
- **The webcam is asked only when a print ends**, for one frame, and never when `snapshots = false` is set for the printer.
- **A timelapse video is attached only with Pro, and only from moonraker-timelapse.** When Moonraker has the `timelapse` component (moonraker-timelapse), the video it renders of a print in the 10 minutes around its end is attached to that print. Without Pro the bridge asks whether you have it, and nothing more: the video is never read or uploaded. Without the component, or with `timelapse = false` for the printer, nothing about timelapses is asked or sent. Only a `.mp4` directly in moonraker-timelapse's own folder is read, and only an MP4 is sent; one over `max_attachment_mb` (100 MB by default) is skipped.

Tests: `TestSpoolCalls` assigns spools by tag and by id and checks each call and field, and that the printer is sent back as read. In `tests/test_own_spoolman.py`, `TestReadOnly` and every test of `TestWithThePrintLogApi` check that nothing was written to Spoolman or Moonraker, and `test_a_spool_matched_by_its_tag` that 3D Print Log was sent only the spool's id and tag. `TestWhatIsSent` runs a whole print through the bridge and checks every call against this table and every field against these lists, that the only images uploaded are the thumbnail and the webcam frame, that the only ranges of the G-code file asked for are the header and the settings block, that no toolpath is sent, and that the settings are sent once, scrubbed, and reach no log, trace or state file. `TestOnlyTheHeaderAndSettingsAreRead` checks the ranges in local mode, that with `slicer_settings = false` the G-code file is never asked for, and points a thumbnail at the G-code file itself; `test_with_snapshots_off_the_webcam_is_never_asked` does what it says. `tests/test_moonraker_slicer.py` reads real OrcaSlicer and PrusaSlicer files, checking every range against where Moonraker says the G-code is, and `tests/test_slicer_settings.py` the scrubbing, every line break included. `tests/test_notifier.py` runs the bridge against a Moonraker with the old notifier set up, and checks that its URL and key reach neither the log, `status.json`, `status` nor `doctor`, and that nothing about it reaches 3D Print Log. `test_a_timelapse_goes_to_storage_with_only_the_listed_fields_and_no_secret` runs a print with moonraker-timelapse and Pro, and checks its calls and fields, that storage gets neither key, and that no secret, the upload address's signature included, is logged or kept. In `tests/test_timelapse.py`, `TestTheWholeBridge` checks that nothing is asked without the component, with `timelapse = false`, or (beyond the plan) without Pro, and `test_never_reads_outside_the_timelapse_folder` what it says.

### The heartbeat

Each heartbeat also tells 3D Print Log how the bridge is doing, so the app can show a printer whose prints aren't getting through, and so 3D Print Log can see which Klipper and Moonraker versions cause trouble. It goes only to 3D Print Log, in the same request as the heartbeat. **There is no third-party telemetry**: no analytics service, no crash reporter, nothing else is contacted. These are all of its fields, sent with every heartbeat (`null` when not known yet, except the software fields, which are left out until known):

| Field | What it is |
| --- | --- |
| `mode` | `local` (Moonraker's socket on this host) or `remote` (Moonraker over the network). Never the address. |
| `firmwareName`, `firmwareVersion` | the printer's firmware and its version, at most 50 characters each: `Klipper` and the version Moonraker reports (`software_version` in `printer.info`), `Bambu` and a Bambu printer's firmware version (its `ota` module in `get_version`), or `Prusa-Firmware-Buddy` (`Prusa-Firmware` behind PrusaLink on a Raspberry Pi) and the `firmware` in PrusaLink's `/api/version` |
| `hostSoftwareName`, `hostSoftwareVersion` | the software the bridge talks to on the printer's host and its version, at most 50 characters each: `Moonraker` and its version (`moonraker_version` in `server.info`); `PrusaLink` and its version (`api` in `/api/version` on Buddy firmware, `version` on a Raspberry Pi); never sent for a Bambu printer, which the bridge talks to directly |
| `printerModel` | the printer model the slicer wrote in the last job's file (`printer_model`, such as `InfiMech EX`), when it wrote one, at most 100 characters |
| `outboxDepth` | how many events and pictures for this printer are waiting in the outbox to be sent |
| `outboxOldestAgeSeconds` | how long the oldest of them has waited, in seconds |
| `lastError` | the last warning or error the bridge logged for this printer, scrubbed (below), at most 300 characters |
| `lastErrorAt` | when that was, in UTC |
| `errorCount` | how many warnings and errors it logged for this printer since the last heartbeat that got through |
| `snapshots` | whether a webcam frame is added to each print (`snapshots` in the config) |
| `slicerSettings` | whether each print's slicer settings are sent (`slicer_settings` in the config) |

`kind` is the adapter (`moonraker`, `bambu` or `prusalink`). A problem that names no printer (the state directory is full, say) counts for every printer.

**No host names, IP addresses, file names or keys are in a heartbeat.** The bridge asks Moonraker for `printer.info` only for Klipper's version, and drops the host name beside it. Before `lastError` leaves the printer, the bridge removes from it every key and password it knows of, every URL, path, IP address, `host:port`, dotted name (`u1.local`, `benchy.gcode`), quoted text (which is how file names turn up in messages) and the names of your printers, leaving only what went wrong, such as `couldn't send the heartbeat: can't reach 3D Print Log at <url>: Cannot connect to host <ip> ...`. The bridge's own log keeps the full message.

Tests: `TestWhatIsSent` runs a print with a failing heartbeat and checks that every heartbeat carries exactly these fields, what each one holds, and that none holds the API or Moonraker key, a password, Moonraker's address or host name, the file name or the state directory. `tests/test_health.py` checks the scrubbing of each kind of host, address, path and file name, and `tests/test_heartbeat.py` each field.

## Where it connects

The bridge only makes outbound connections, to:

1. **Moonraker**: its Unix socket in local mode, or the `url` you set in remote mode (HTTP and WebSocket, on your network). In remote mode it also downloads the thumbnail from Moonraker's file API, and the two byte ranges of the G-code file that hold its header and settings (unless `slicer_settings = false`), and with Pro the timelapse video.
2. **The webcam's `snapshot_url`**, as Mainsail or Fluidd have it set in Moonraker (usually the printer itself), when a print ends.
3. **3D Print Log**, at `api_url` (`https://api.3dprintlog.com` by default), **over HTTPS only.** The config refuses a plain `http://` `api_url`, except to this computer itself (`localhost`, `127.0.0.1`, `::1`), for a test server or a TLS proxy on the same host. With `allow_http_on_lan = true` (or `PRINTLOG_ALLOW_HTTP_ON_LAN=1`) it also accepts plain http to a private-network IP address (RFC 1918 `10/8`, `172.16/12` and `192.168/16`, link-local `169.254/16` and `fe80::/10`, IPv6 unique local `fc00::/7`), for a development API on your own network; the API key then travels unencrypted on that network, so `run` logs a warning every time it starts and `doctor` shows one. A public address, a host name, or any other address Python calls private (Teredo, documentation and reserved ranges) is refused either way.
4. **Moonraker's port on your local network, to find a printer again** (remote mode, unless `discovery = false`). When a printer can't be reached for 3 minutes (`discovery_after`), or a different printer answers at its address, the bridge looks for it, at most once every 10 minutes (`discovery_interval`, never more often than every 30 seconds). It sends one mDNS query for `_moonraker._tcp` to the local multicast group (224.0.0.251), then asks each address of the printer's last known /24 for `GET /server/info` on Moonraker's port, and a Moonraker that answers for `GET /machine/system_info`, to compare its MAC addresses with the printer's. `discovery_zeroconf = false` skips the mDNS query, and `discovery_networks` names the networks to scan instead. It only ever looks on private IPv4 networks (RFC 1918), each a /24 or smaller (the config refuses anything else), and reads nothing else. `moonraker_api_key`, when set, goes only to an address that has already answered as Moonraker, or asked for authorization, on that port. It never connects its WebSocket, or logs anything from, a printer whose identity doesn't match. What it remembers (the MAC addresses and the printer's IP addresses) stays in the printer's state file; never a password from the `url`.

5. **3D Print Log's file storage**, with Pro and moonraker-timelapse: the address 3D Print Log gives for each video, over HTTPS (plain http only when `api_url` itself is a plain http development API).

`printlog-bridge discover`, which you run yourself, does the same over the networks you name with `--subnet` (or the configured printers' and this computer's own), and also reads `/printer/info` and `/printer/objects/list` from each Moonraker that answers, to show its host name, Klipper version and tool count. It sends no keys.

**It never checks for updates anywhere else.** The latest version comes back in the heartbeat's answer, and `update_check = false` only stops the bridge from saying so: what it sends stays the same.

6. **A Bambu Lab printer** (`adapter = bambu`): its MQTT broker at `host`, port 8883, over TLS, and its FTPS server, port 990, implicit TLS. See [Bambu Lab printers](#bambu-lab-printers).

7. **A Prusa printer's PrusaLink** (`adapter = prusalink`): its web API at `host` (port 80 unless `port` says otherwise), plain HTTP, GET requests only. See [Prusa printers (PrusaLink)](#prusa-printers-prusalink).

8. **OctoPrint** (`adapter = octoprint`): its REST API and push socket at `url`, as given (usually plain HTTP on your network), and the webcam's snapshot URL OctoPrint has, when a print ends. See [OctoPrint](#octoprint).

9. **An Elegoo Centauri Carbon** (`adapter = sdcp`): its websocket at `host`, port 3030 (`ws://`, plain, as Elegoo's own slicer connects), and its web server at `host`, port 80 (`http_port`), for the start of each print's file (`files = false` turns that off). See [Elegoo Centauri Carbon (SDCP)](#elegoo-centauri-carbon-sdcp).

10. **A Duet board** (`adapter = duet`): its web API at `host` (port 80 unless `port` says otherwise), plain HTTP, GET requests only, or DuetSoftwareFramework's on the board's Raspberry Pi at the same address. See [Duet / RepRapFirmware](#duet--reprapfirmware).

11. **3D Print Log's sign-in service (Auth0), only while pairing**: the two addresses 3D Print Log's API names for it (`https://auth.3dprintlog.com/oauth/device/code` and `/oauth/token`), **over HTTPS only**: the bridge refuses any other. It asks for a code with 3D Print Log's public app id, the API it's for and the permissions the bridge needs, then asks every few seconds (as slowly as the service says) whether you approved it. It never asks for `offline_access`, so there is no refresh token. It sends no API key, password, or anything about your printers. The service sees this computer's network address, and, when you approve the code, your sign-in, as when you sign in to the website. The access token it gives is used once, to get the device token from 3D Print Log, and is never stored or logged.

12. **An Anycubic printer in LAN mode** (`adapter = anycubic`): its handshake at `host`, port 18910 (plain HTTP: `GET /info`, `POST /ctrl`), then its MQTT broker over TLS at the same address. See [Anycubic (LAN mode)](#anycubic-lan-mode).

13. **Your local network, to find printers** (paired, unless `discovery = false`): an mDNS query every 5 minutes, and Moonraker's `/server/info` on each Moonraker that answers it; the scan you ask for in the app. See [Discovery and check-in](#discovery-and-check-in).

It **opens one TCP port, for the local page**: `127.0.0.1:7180` by default, so only this computer can connect (`status_page` moves or turns it off; see [The local page](#the-local-page)). It listens on one UDP port only: 2021, for Bambu Lab printers' announcements, while a paired bridge runs with discovery on (in Docker only on the host's network; it says so in its log when it can't), and while `printlog-bridge discover` runs (6 seconds, unless `--no-bambu`). It sends nothing in answer. Asking Elegoo printers (`M99999`, in a scan you start in the app and in `printlog-bridge discover` unless `--no-sdcp`) and Anycubic printers (an SSDP search, likewise, unless `--no-anycubic`) binds no port: the question goes out from an ephemeral port, and the answers to it are read for 3 seconds.

Tests: `test_connects_only_to_moonraker_its_webcam_and_3d_print_log` records every connection during a print, and the timelapse test above during one with a video. In `tests/test_discovery.py`, `test_a_different_printer_at_the_old_address_is_never_used` puts another printer at the old address, `test_with_discovery_off_the_printer_isnt_identified_or_looked_for` checks the off switch, `test_the_moonraker_key_goes_only_to_an_address_that_answers_as_moonraker` and `test_no_password_in_the_url_reaches_the_state_file` what they say, and `TestAddresses` that only private networks of a /24 or smaller are searched. `TestOnlyOutboundConnections` fails if any code in the bridge starts a server or listens on a socket, if a module other than the API client, the image fetcher, the Moonraker session, discovery, the printers' own clients and pairing opens a connection, or if `api_url` accepts plain http to another host (beyond a private-network address with `allow_http_on_lan`, which `TestPlainHttpOnTheLanIsWarnedAbout` checks is warned about).

## The local page

`run` serves a read-only page (`core/local_page.py`) with what `status` and `doctor` say and, while pairing, the code to approve. It runs in a thread of its own, so it can't hold up or stop the bridge.

- **Where:** `127.0.0.1:7180` by default (this computer only); `status_page` in `[bridge]` (or `PRINTLOG_BRIDGE_STATUS_PAGE`) sets another address or port, or `off`. `status_page_clients` (or `PRINTLOG_BRIDGE_STATUS_PAGE_CLIENTS`) limits it to those IP addresses. The Home Assistant app sets `0.0.0.0:7180` for the Supervisor's ingress proxy only (`172.30.32.2`); it's on the host's network, so the port is open on the host, and everyone else gets 403.
- **What it never shows:** an API key, the device token, a printer's password, access code or API key (from the config or sealed in the app), the device code that polls for the token, or the bridge's private key. It shows the key's fingerprint, as `status` does. Everything it shows also goes through the same scrubbing as the support bundle, and every value is HTML-escaped (printer names come from the network).
- **What it shows anyone who can open it:** the bridge's status, its version, the config's path, your printers' names and addresses, `doctor`'s results, and, while pairing, the code to approve. Whoever approves that code first gets the bridge in their account: keep the page off a shared network. On a shared host, `127.0.0.1` is open to every user of that host too: pair from a host you control, or set `status_page = off`.
- **Requests:** `GET` and `HEAD` of `/` and `/doctor` only, nothing else (405, 404); no form, no cookies, no scripts. `/doctor` starts the checks (the API, each printer) in the background, at most every 30 seconds and one run at a time, and refreshes until they're done; no request waits for them. A request another site's page makes is refused (403): `Sec-Fetch-Site` must be `same-origin` or `none` and `Sec-Fetch-Dest` `document` or `iframe` when the browser sends them. A config with an error is never quoted (its line can hold a secret): the page says to look at the log. A request whose `Host` is a public name is refused (421), against DNS rebinding, unless `status_page_clients` is set. A connection from an address `status_page_clients` doesn't list is closed as it's accepted, before it's read or takes one of the 8 request slots, and every connection must send its request line and headers within 10 seconds. Every answer carries `Content-Security-Policy: default-src 'none'` (with a per-answer nonce for its own style), `frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN` (Home Assistant shows ingress pages in a frame of its own origin), `X-Content-Type-Options: nosniff`, `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

Tests: `tests/test_local_page.py` (`TestSecrets` puts every secret in the config, the state directory, the status file and doctor's results and checks none reaches either page; `TestWhoMayOpenIt`, `TestHeaders`, `TestIngress`), `test_run_serves_the_local_page_with_the_code_to_approve_while_it_pairs` (`tests/test_run.py`), and `TestOnlyOutboundConnections` above, which allows a listening socket only there and checks the default stays `127.0.0.1`.

## Discovery and check-in

A paired bridge (a device token with the `bridge:sync` permission) checks in with 3D Print Log, so the app can show the bridge, what it found on your network ("Found on your network") and let you connect printers to it. `discovery = false` in `[bridge]` stops the looking; the check-in then carries no `discovered`.

**What it reports of your network is only the printers an adapter recognizes**, never any other host: a Moonraker that answered `/server/info` as Moonraker, a PrusaLink or OctoPrint host that advertised itself as one, a Bambu Lab printer's own announcement, an Elegoo printer's answer to `M99999`, a web server whose mDNS answer says it runs RepRapFirmware, an Anycubic printer's answer to an SSDP search for `ac:3dprinter`. For each, `discovered` carries exactly: `kind` (`moonraker`, `bambu`, `prusalink`, `octoprint`, `sdcp`, `duet` or `anycubic`), `address` (a private IP address: RFC 1918, link-local or IPv6 unique local, never a public one), `port`, `model` and `name` (what the printer calls itself: its host name, a Bambu printer's name and model, a PrusaLink printer's mDNS name and type, an OctoPrint's mDNS name and the vendor and model it was given, an Elegoo printer's name and model, an Anycubic printer's model, a Duet's mDNS name and the board its TXT record names), `serial` (a Bambu or Anycubic printer's serial; a PrusaLink printer's when it advertises one; an OctoPrint's instance id, its `uuid`), `mainboardId` (an Elegoo printer's, from its answer), `macs` (an Anycubic printer's MAC address from its SSDP answer; a Moonraker host's network interfaces' MAC addresses, as Moonraker reports them, to tell it apart after an address change) and `configured` (whether a `[printer]` section of your config already watches it). The printers in your config file are reported too, with `configured: true`, so the app shows them as managed by the config. At most 50 printers; one not seen for 30 minutes (24 hours when only a scan found it) is left out.

**How it looks:** one mDNS query every 5 minutes for `_moonraker._tcp`, `_prusalink._tcp` (and `_prusa-link._tcp`) `_http._tcp` (kept only for an answer whose TXT `product` names RepRapFirmware or a Duet: every other web server's answer is dropped, and none is asked anything) and `_octoprint._tcp` (PrusaLink on a Raspberry Pi also answers to that one: an answer with OctoPrint's `api` and `version` is OctoPrint, one without them that names Prusa is PrusaLink, and one with no TXT at all is OctoPrint unless it's named PrusaLink; neither is asked anything, and an OctoPrint's HTTP basic auth user and password, which its answer can carry, are dropped), sent from an ephemeral port to 224.0.0.251:5353, and the answers read; it binds nothing on 5353. It listens on UDP port 2021 for Bambu Lab printers' NOTIFY announcements, and sends them nothing. Each Moonraker that answers mDNS is asked, once, `GET /server/info`, `/machine/system_info`, `/printer/info` and `/printer/objects/list` (no key). **A scan runs only when you tap "Scan now" in the app**, at most once a minute: the same per-address scan as `printlog-bridge discover`, on Moonraker's port 7125, over the networks in `networks`, each a /24, and the text `M99999` sent once to each of those networks' broadcast address and to 255.255.255.255, UDP port 3000, from an ephemeral port, with the answers read for 3 seconds (each Elegoo printer answers with its name, model, mainboard id and firmware version; it is asked nothing else). The same scan sends an SSDP M-SEARCH for `ac:3dprinter:fdm` and `ac:3dprinter:lcd` to 239.255.255.250 and each network's broadcast address, UDP port 1900, and reads the answers for 3 seconds (each Anycubic printer in LAN mode answers with its model, serial, MAC address and an `/info` token, which is dropped).

**It never watches a printer because it found it.** It watches only the printers in your config and the ones you connected to it in the app (the answer to the check-in, and `GET /api/bridges/me/desired`), and the config wins when both name one. A printer connected in the app by a host name is watched only when every address the name resolves to is private. Its password or access code comes from the app sealed to the bridge (below), or from the config file (`[app_printer <number>]`), which stays on the bridge.

The check-in also carries the bridge's **public** key and its fingerprint (`publicKey`, `publicKeyFingerprint`), and, once it has applied a list of connected printers, `credentialIssues`: for each printer and credential field the bridge can't use, only the entry's number, the field's name and a code (`missing`, `undecryptable`, `invalid_plaintext`, `rejected_by_printer`), never a value. `credentialIssuesVersion` names the list they describe.

What it remembers is in `bridge.json` in the state directory: the last list of connected printers (with their credentials as 3D Print Log sent them, sealed: only the bridge's key opens them), the bridge's number in 3D Print Log, when it last scanned, and whether it already paired again for the permission (a hash of the device token, never the token).

Tests: in `tests/test_bridge_sync.py`, `test_the_check_in_carries_what_the_contract_lists` checks every field, `test_nothing_the_bridge_sends_can_set_its_own_desired_list` what it says; `tests/test_lan_discovery.py` that only what a hook recognizes is kept and never a public address; `test_never_watches_what_it_only_found` in `tests/test_app_printers.py` that a printer found isn't connected to, and `TestBridgeCheckIn` in `tests/test_privacy.py` that the check-in carries only the fields above and no key.

## Printer credentials entered in the app

A printer connected in the app may need an access code (Bambu Lab), a password or API key (PrusaLink), a password (a Duet with `M551`) or an API key (Moonraker with `[authorization]`). You enter it on the bridge's page in 3D Print Log, and **3D Print Log can't read it**:

- **The bridge's key.** The bridge makes one P-256 key pair and keeps the private key in `credential-key.pem` in its state directory (mode 600, readable only by the bridge's user). The private key never leaves the bridge: it isn't sent, logged, traced, shown by `status` or `doctor`, or put in the support bundle. Only the public half goes to 3D Print Log, on every check-in.
- **Sealed in your browser.** The web app encrypts each value to that public key (ECDH P-256, HKDF-SHA256, AES-256-GCM, a fresh key per value) before it leaves the browser, tied to this bridge, that printer and that field. 3D Print Log, its database and its backups hold only the sealed value, and send it only to this bridge. The scheme is specified in 3d-print-log-api's `docs/bridge-credential-sealing.md`; `tests/test_credentials.py` checks the bridge against its test vectors.
- **Opened on the bridge, in memory only.** The bridge opens a value when it starts watching the printer and keeps it in memory, never in a file (`bridge.json` keeps the sealed form). It uses it exactly as you typed it, and sends it only to that printer, as the adapter sends any password. It's scrubbed from traces and logs like a key, and the support bundle removes it too.
- **Comparing fingerprints.** 3D Print Log could, in principle, hand your browser another key than the bridge's. So the app shows the fingerprint of the key it encrypts to, computed in your browser, and the bridge shows its own (`printlog-bridge status`, `doctor`, `pair`: `Encryption key: aed0 3e9a 8282 33b2`). When the app asks you to confirm a bridge's key, check the two match. Only the key the bridge sends right after you pair it is trusted without that check; any other (an update from a bridge without a key, a new state directory, `printlog-bridge rotate-key`) waits for your confirmation, and `status` says `waiting for confirmation in the app` until you give it.
- **What it doesn't protect.** Anyone with the public key can seal a value the bridge accepts, so a value from the app is trusted as much as 3D Print Log is; that's one reason a value in the config file wins. A sealed value is as long as the credential (an 8-digit access code looks like one).

Losing the state directory loses the key: the bridge makes a new one, you confirm it in the app and enter the credentials again.

## Your keys and passwords

The bridge holds up to four kinds of secret: your 3D Print Log API key, Moonraker's API key (`moonraker_api_key`, remote mode only), any password or token in a Moonraker or webcam URL (`http://user:password@host`, `?token=...`), a Bambu printer's LAN access code (`access_code`), a PrusaLink printer's password or API key (`password`, `api_key`), and a Duet's password (`password`), each also in an `[app_printer <number>]` section for a printer connected in the app, or from the app, sealed to the bridge's own key (above).

**The API key is kept out of the folder Moonraker serves.** In local mode, `printlog-bridge.cfg` sits in Klipper's config folder, and Moonraker lets anyone who can open Mainsail or Fluidd read and download every file in it. So:

- `install.sh` stores the key in `~/.local/share/printlog-bridge/api_key` (the bridge's state directory), mode 600 so only you can read it, and never writes it into `printlog-bridge.cfg`.
- `printlog-bridge store-key` stores or replaces the key there. Run it on an older install to move `api_key` out of `printlog-bridge.cfg`: it writes the key file and empties the line in the config. Run it as the user the bridge runs as, never with `sudo`. When it has an `api_key` to move out of the config, it refuses, before writing anything, unless the config belongs to the user running it: otherwise the key file would be another user's and the rewritten config root's or out of reach. A config an earlier `sudo store-key` left to root gets a `sudo chown` to give it back. A config with no `api_key` isn't rewritten, so a service user can store its key next to a root-owned `/etc` config. Root may only store a key for root's own config, in a folder only root can write, from a root login rather than through `sudo`, since the key file goes where that config says. The config is read, checked and rewritten through its folder held open, so renaming files in between can't redirect it, and a symlinked config stays a symlink.
- In the Docker image, `store-key` keeps it in `/data/state/api_key` in the mounted folder, mode 600, owned by the user the container runs as. The image itself never holds a key; `PRINTLOG_API_KEY` can be set on the container instead, where anyone who can manage the host's containers can read it.
- The bridge looks for the key in this order: the `PRINTLOG_API_KEY` environment variable, the key file, then `api_key` in `[bridge]`. A key in the config still works, so existing installs keep running.
- `doctor` warns when `api_key` is in a config file Moonraker serves (even an unused one), when the key file is in a folder Moonraker serves, and when other users on the computer can read the key file.

A Bambu printer's `access_code` stays in the config too: the bridge sends it only to that printer (as the MQTT and FTPS password, each only after the printer's certificate matched the pinned one), and it is scrubbed like a key everywhere the bridge writes. `doctor` warns when a printer's `access_code` is in a config file a printer's host serves (Klipper's config folder): anyone who can open Mainsail or Fluidd could read it and control the Bambu printer.

A PrusaLink printer's `password` or `api_key` stays in the config too, is sent only to that printer, and is scrubbed like a key everywhere the bridge writes; `doctor` warns about it as about `access_code`.

**A paired bridge holds a device token instead of an API key.** `printlog-bridge pair` (and `run`, the first time it has no credentials) gets it from 3D Print Log once you approve the bridge on 3D Print Log's sign-in page:

- It is kept in `device_token` in the state directory, mode 600, never in the config, with the address of the API that issued it. It is sent only to that API: after a change of `api_url` it isn't used at all (`doctor` says so), so it can't be sent anywhere else. When a device token is there, the bridge sends it and never the API key.
- It works only on the calls the bridge makes (the table above), and only with the permissions the bridge asked for: it can't delete a print or a spool, or read anything else of your account. It has no expiry; you remove it in 3D Print Log, which takes effect on the bridge's next request. The bridge then stops sending, keeps every job in its outbox, and says "re-pair needed" in its log, `status` and `doctor` until `printlog-bridge pair` gets it a new one (which it picks up without a restart). Pairing again replaces the token; the old one stops working.
- `device_id` next to it is the bridge's own random id, not a secret: pairing again sends the same one, so 3D Print Log keeps one entry for the bridge instead of adding another.
- While pairing, the code to approve and a QR code of its address go to the terminal, or to the log on the first run (`docker logs`, a Home Assistant app's Log tab). Anyone who reads them before you approve could approve the bridge into their own account instead, so the code works for only about 15 minutes, and once. While it waits, the code and its address (never the device code that polls for the token) are also in `pairing_pending.json` in the state directory, mode 600, for `printlog-bridge status --pairing`, which the one-line Docker install reads; the file goes when pairing ends.
- The token is scrubbed like a key everywhere the bridge writes, and the support bundle never includes `device_token`.

**In the Home Assistant app** (`home-assistant/`), you enter the secrets in the app's options, as password fields. Home Assistant keeps the options with the app's settings and writes them to `/data/options.json` before each start; `/data` is the app's private folder, which Home Assistant never serves. The app's start-up (`printlog-bridge-addon`) then:

- passes the 3D Print Log API key to the bridge in `PRINTLOG_API_KEY`, never in a file;
- writes the printers' secrets (`access_code`, `password`, `api_key`) into `/data/printlog-bridge.cfg`, mode 600, owned by the user the bridge runs as (not root);
- never prints an option's value: the app's Log tab shows only how many printers it watches and their names, and an option it refuses is named, never shown;
- deletes a device token 3D Print Log refused (removed in the app, or replaced), so restarting the app pairs it again.

A Home Assistant backup of the app includes `/data` (the options, the config, the device token and the outbox), but not `bridge.log`, traces or the support bundle (`backup_exclude`). Home Assistant encrypts backups by default since 2025.1. The app runs on the host's network, as `--network host` does in Docker, only to find printers; it still opens no ports. Tests: `tests/test_addon.py` (the API key in no file, the config's mode, nothing secret in the start-up's output or errors) and `tests/test_ha_app.py` (password fields, backup exclusions).

`moonraker_api_key` stays in the config. It is only for remote mode, where the bridge usually runs on another computer, away from any folder Moonraker serves; `doctor` doesn't check where it is.

**Secrets never reach the log, the status file, `status`, `doctor`, a trace or the support bundle.** URLs are shown with their user, password and secret-looking query values (`token`, `key`, `pass`, `auth`, `sig`, `user`, ...) replaced by `***`, in `bridge.log`, `status.json`, `status`, `doctor`, and every error message. An error that repeats a URL has the same parts hidden in any URL it writes, and each such secret hidden wherever else it appears, as configured, decoded or re-encoded (aiohttp writes `%2f` as `%2F`, for one). A secret under 3 characters, such as the user `pi`, is hidden only inside a URL, so a host name such as `pi.local` stays readable. The support bundle `doctor` writes removes every key, token and password it knows of (from the config, the key file and the environment) from every file in it, as well as passwords in URLs and secret-looking query values, and never includes the key file.

Tests: `test_no_secret_reaches_the_log`, `..._the_state_directory` and `..._status` run a print, traced, with every kind of secret set and look for each in everything the bridge wrote, the trace included. `TestMoonrakerUrlsAreMasked` covers `doctor`'s messages, `TestSupportBundle` here and in `tests/test_doctor.py` the bundle, `tests/test_install_helper.py` and `tests/install/smoke.sh` where install.sh puts the key, and `TestApiKeyStorage` in `tests/test_doctor.py` the warnings. For a device token, `tests/test_device_token.py` checks it is the only credential sent, never one from another API, and never in the support bundle; `tests/test_pairing.py` that `offline_access` is never asked for, the sign-in addresses must be https and the file is mode 600; `tests/test_repair_needed.py` that a removed token stops all sending and keeps the jobs; `tests/test_doctor_device.py` the warnings.

## What it keeps on the printer

In the state directory (`~/.local/share/printlog-bridge` by default): the key file, the device token and the bridge's id (`device_token`, `device_id`), which job it logged as which print, and each remote printer's identity and last found address (`printers/`), the outbox of events, pictures, slicer settings (scrubbed) and timelapse videos not yet sent (`outbox.sqlite3`, `images/`, `attachments/`; a sent entry is overwritten in the file, not just marked free, and a picture's or video's file is deleted once sent or given up on), `status.json` and `bridge.log`, and with `trace = true`, the traces (`traces/`). An event still unsent after 30 days is dropped. `uninstall.sh --purge` removes all of it.

### Traces

Tracing is off unless you set `trace = true` in `[bridge]` (or `PRINTLOG_BRIDGE_TRACE=1`). Then the bridge records every message it sends to and receives from each printer's Moonraker in `traces/<printer>-<YYYYMMDD>.jsonl`. **Traces stay on this computer**: the bridge never sends them anywhere. The only way one leaves is in the support bundle `doctor` writes (the latest 20 MB), which you choose to attach.

What a trace holds is what Moonraker tells the bridge, and what the bridge asks it:

- the printer's state as it changes: print progress, the active tool, filament used, Klipper's state, on a U1 its RFID reader's tags, each tool macro's `spool_id` and your `[save_variables]`;
- with a Spoolman server of your own, the record of each spool that became active, as Spoolman returns it through Moonraker (its filament, vendor, weights, price, location, lot and comment);
- Moonraker's job history: file names (with their folders), times, outcomes and the slicer's metadata;
- the printer's list of objects, its webcams (their URLs, scrubbed), and lines printed to the console;
- Moonraker's and Klipper's versions, and the host name Klipper reports beside its version (`printer.info`);
- the bridge's own requests, such as which objects it subscribes to.

It holds nothing of Moonraker's config: the answer to `server.config` (all of moonraker.conf, `[spoolman] server` and notifier URLs included) is replaced by `<redacted>` whole, since an Apprise URL such as `tgram://<bot>:<token>/...` holds its token where no scrubber can tell it apart.

It holds no G-code, and none of the header or settings block read for the slicer settings: those are read outside the connection that is traced. The support bundle's copy of the outbox (`outbox.json`) leaves their text out too, keeping only its length. Before a line is written, every secret the support bundle removes is removed from it: your 3D Print Log API key, Moonraker's API key, passwords in URLs and secret-looking query values (a webcam's `?token=`), any field named like a key, token, secret or password, and Moonraker's answer to a request for a oneshot token or API key, or for its config. The support bundle scrubs traces a second time.

Each printer's traces stay under 50 MB, the oldest deleted first. Recording never slows the bridge, and a disk error never stops it. Turn tracing off and delete `traces/` whenever you like.

Tests: `tests/test_trace.py` (each kind of secret, the size cap, a stuck or failing disk), `TestWhatIsSent` (a traced print, checked for every secret), and `TestSupportBundle` in `tests/test_doctor.py`.

## Bambu Lab printers

With `adapter = bambu`, the bridge connects to the printer itself, as Bambu Studio does in LAN mode, and to nothing of Bambu's: no Bambu cloud, no Bambu account.

- **MQTT (port 8883, TLS).** It logs in as `bblp` with the access code, subscribes to the printer's status reports, and publishes only two requests: `get_version` (the firmware version) and `pushall` (send the whole status), on each connect, and `pushall` again every 30 minutes. It never sends a command that changes anything on the printer.
- **FTPS (port 990, implicit TLS), unless `ftps = false`.** When a job starts printing, it downloads that job's 3MF (at most 200 MB) into a temporary file, which is deleted when the next job's is fetched or the bridge stops. It reads three entries from it: `Metadata/slice_info.config` (the slicer's grams and meters per filament and its time estimate), `Metadata/plate_<n>.png` (the plate's thumbnail, sent as the print's picture), and, only when the slicer settings are sent (not with `slicer_settings = false`), `Metadata/project_settings.config`, turned into `; key = value` lines and scrubbed like a G-code file's settings. The model and the toolpaths in the 3MF are never read or sent, and nothing is ever written to the printer.
- **What 3D Print Log gets** is what it gets from a Klipper printer: the print's file name (`<name>.3mf`, without folders), times, outcome, the slicer's estimates, grams and meters per AMS tray (marked as estimates), the thumbnail and the settings, plus the AMS's RFID tag UID, material and color for each tray (a tag is looked up with `GET /api/Filaments/by-tag/{uid}`). Never the serial, the access code, the printer's address or its name.
- **The certificate.** The printer's certificate is from Bambu's own CA, which nothing else trusts, so the bridge pins the first one each service shows (its SHA-256, in the printer's state file) and refuses to send the access code to a printer that shows another. The first connection is trusted as it comes; set `tls_fingerprint` to pin it yourself.
- **Traces** of a Bambu printer hold its status reports as the printer sends them: job and file names, progress, temperatures, fans, the AMS's trays (tag UIDs, materials, colors, humidity), error codes, the firmware versions and module serials of `get_version`, and whatever network details the firmware puts in its reports. Never the access code: it is scrubbed, as is any field named `access_code`.

Tests: `test_the_bridge_logs_a_bambu_print_with_the_slicers_grams_per_tray` (`tests/test_bambu_adapter.py`) runs a print through the whole bridge from the fake printer and checks the usage rows, and that the access code isn't in the status file; `test_a_bambu_access_code_in_the_config_is_a_known_secret` (`tests/test_secrets.py`) and `test_a_field_named_access_code_is_removed` (`tests/test_trace.py`) the scrubbing; `TestPrinterSecretStorage` in `tests/test_doctor.py` the warning; `TestCertificatePin` and `test_the_certificate_is_checked_before_the_access_code_is_sent` in `tests/test_bambu_mqtt.py`, and `test_the_certificate_is_checked_before_logging_in` in `tests/test_bambu_files.py`, that the access code is never sent to another certificate.

## Prusa printers (PrusaLink)

With `adapter = prusalink`, the bridge connects to the printer itself, over PrusaLink's local web API, and to nothing of Prusa's: no Prusa Connect, no Prusa account.

- **Requests.** Only `GET`: `/api/version` once per connect (the firmware), `/api/v1/status` every 5 seconds during a job and every 30 seconds between jobs, `/api/v1/job` once per job (its file's name and links), and, unless `files = false`, the job's file and its thumbnail. It never starts, pauses, stops, uploads or deletes anything.
- **The password.** PrusaLink asks for HTTP Digest: the password itself never crosses the network, only a hash of it with a one-time nonce. Firmware that asks for an API key gets `X-Api-Key`, which does cross the network as it is, over plain HTTP, as the printer's own web page sends it.
- **The file.** For a `.bgcode` file the bridge reads it from the start and stops at its first G-code block, keeping the metadata (the slicer's estimates and the printer model), the largest thumbnail and the slicer settings block. A plain `.gcode` file is read whole (at most 64 MB) and only its first 64 KB and last 512 KB are kept, in memory: its header and the comments after its last G-code command. The toolpaths are never kept or sent. The settings are scrubbed like any G-code file's, and sent only with `slicer_settings` on.
- **What 3D Print Log gets** is what it gets from a Klipper printer: the file's name (without folders), times, outcome, the slicer's estimates (grams and millimeters per tool, marked as estimates), the thumbnail, the settings, and the printer model the slicer wrote. Never the printer's address, serial, host name or password.
- **Traces** of a PrusaLink printer hold each request's path, and each answer's status and JSON body: the printer's state, temperatures, fans, job number, progress and times, the job's file names and links, the firmware and host name in `/api/version`, and the challenge of a 401 (realm and nonce). Never a request's headers, so never the password, the key or the Digest answer, and never a file's contents.

Tests: `test_the_bridge_logs_a_prusalink_print_with_the_slicers_grams` (`tests/test_prusalink_adapter.py`) runs a print through the whole bridge from the fake printer, checks the usage rows, that only `GET` reached the printer, and that the password isn't in the status file; `test_a_prusalink_password_and_api_key_in_the_config_are_known_secrets` (`tests/test_secrets.py`) and `test_a_prusalink_session_is_traced_without_its_password` (`tests/test_trace.py`) the scrubbing; `test_a_bgcode_file_is_read_up_to_its_gcode` (`tests/test_prusalink_files.py`) that the download stops at the G-code.

## OctoPrint

With `adapter = octoprint`, the bridge connects to OctoPrint at `url`, and to nothing else of OctoPrint's: no plugin repository, no OctoPrint account.

- **Requests.** `GET /api/version` and `GET /api/settings` on each connect (OctoPrint's version; the webcam's snapshot URL; whether the Webhooks plugin posts to 3D Print Log), `POST /api/login` with `passive` (which only says who the key belongs to and gives a session for the socket: it logs no one in and changes nothing), then the socket `/sockjs/websocket`, which only receives once it is authenticated. Per print, two byte ranges of its file (`/downloads/files/local/<path>`, the first 256 KB and the last 512 KB, unless `files = false`) and, without an embedded thumbnail, the file's entry and the PrusaSlicer Thumbnails plugin's picture. It never starts, pauses or cancels a print, uploads, selects or deletes a file, or sends G-code.
- **The key** goes in every request's `X-Api-Key` header, over the `url` you give: plain HTTP on most home networks, as OctoPrint's own web page sends it. The socket's session is never logged or traced. The webcam's snapshot URL gets no key.
- **What 3D Print Log gets** is what it gets from a Klipper printer: the file's name (without folders), times, outcome, the slicer's estimates (grams and millimeters per tool, marked as estimates), the thumbnail, the settings (scrubbed like any G-code file's, and only with `slicer_settings` on), the printer model the slicer wrote, and OctoPrint's version (the heartbeat's host software). Never OctoPrint's address, user name, key or settings, and never the Webhooks plugin's URL.
- **Traces** of an OctoPrint printer hold each request's path and each answer's status and JSON body, but for the login's (its session and key replaced) and `/api/settings`' (only the webcam's snapshot fields and whether a webhook posts to 3D Print Log: never other plugins' settings, which can hold a Discord or Slack webhook's token or the Webhooks plugin's headers), and the socket messages the bridge reads as they came: OctoPrint's state, temperatures, the last terminal lines, the job's file name and path, progress, the print chart's marks and OctoPrint's events. Of any other socket message, such as a plugin's, only its type and the plugin's name. Never a request's headers, so never the key, and never a file's contents.

Tests: `test_the_bridge_logs_an_octoprint_print` (`tests/test_octoprint_adapter.py`) runs a print through the whole bridge from the fake OctoPrint and checks that the key isn't in the status file; `test_a_print_from_start_to_finish` that only `GET` (besides the login) reached OctoPrint and the ranges asked for; `test_a_session_is_traced_without_its_key_or_socket_session_or_other_plugins` the trace and the support bundle; `test_a_sealed_octoprint_key_is_used_and_a_refused_one_reported` (`tests/test_sealed_credentials.py`) a key from the app.

## Elegoo Centauri Carbon (SDCP)

With `adapter = sdcp`, the bridge connects to the printer itself, over the websocket Elegoo's slicer uses (`ws://<host>:3030/websocket`), and to nothing of Elegoo's: no Elegoo cloud, no Elegoo account.

- **No credentials.** SDCP has no authentication: anything on your network can connect to the printer and control it, with or without the bridge. So there is nothing to store, and the bridge **only reads**.
- **Requests.** On each connect, Cmd 1 (send the attributes: the printer's name, model and firmware version) and Cmd 0 (send the status again), with empty data, and the text `ping` every 20 seconds, since the printer drops a client that stays silent. The requests name the printer's mainboard id once the bridge has learned it from the printer's messages (kept in the printer's state file). It never sends any other command: none starts, pauses or stops a print, changes a setting, turns on the camera, or lists, sends or deletes a file. `tests/test_sdcp_adapter.py` checks that the fake printer received nothing else.
- **The job's file.** When a print starts, one HTTP GET to `http://<host>/downloadFile/<path>` (the path the status names) with `Range: bytes=0-262143`: the first 256 KB, where the slicer's header (its estimates, the slicer's name and version) and the thumbnail are. A printer that ignores the range is read no further. Never the rest of the file, never twice for a job, no redirects followed. `files = false` turns it off.
- **What 3D Print Log gets** is the file's name (without folders), times, outcome, the time estimate, the slicer's filament estimate (marked estimated), its thumbnail and header (scrubbed as for every adapter) when the file could be read. Never the printer's address or mainboard id (but in a check-in's `discovered`, above), and the firmware version only in the heartbeat.
- **Traces** of an SDCP printer hold the status pushes as the printer sends them (state, temperatures, fans, position, light, the job's file name and path, task id, layers, times and progress), the printer's acknowledgements of the bridge's two requests, `pong`, and of the attributes only what the bridge reads (name, model, brand, firmware and protocol versions, mainboard id): never the rest, which names your Wi-Fi network and the printer's MAC address. Of any other message, such as a notice, an error or another client's answer, only its kind (and a command's number).

Tests: `test_the_bridge_logs_a_centauri_carbon_print` (`tests/test_sdcp_adapter.py`) runs a print through the whole bridge from the fake printer; `test_a_print_from_start_to_finish` that the printer got only Cmd 0, Cmd 1 and pings; `test_a_trace_keeps_only_what_the_bridge_reads` the trace.

## Duet / RepRapFirmware

With `adapter = duet`, the bridge connects to the Duet board itself, over the HTTP API Duet Web Control uses (plain HTTP, on your network), or to DuetSoftwareFramework on its Raspberry Pi, and to nothing of Duet3D's.

- **Requests.** Only `GET`. Standalone: `rr_connect?password=...` to open a session (never `time=`, which would set the board's clock), `rr_model` every 5 seconds during a job and every 30 seconds between jobs, with a read of the live fields alone every half session timeout (4 seconds) in between so the session doesn't lapse and the password goes out once per connection (the fields that change often, and in full the parts of the object model that changed: `boards`, `job`, `move`, `network`, `sbc`, `state`, `tools`; never `global`, your macros' variables), `rr_fileinfo` once per job and `rr_thumbnail` for its thumbnail (unless `files = false`), and `rr_disconnect` when the bridge stops. With an SBC: `/machine/connect`, `/machine/noop` between polls, `/machine/model` (the whole model, of which the bridge keeps what it reads), `/machine/fileinfo/<file>` and `/machine/disconnect`. It never sends G-code, starts, pauses or cancels a print, or uploads, downloads or deletes a file.
- **The password** (only when the board has one, `M551`) crosses the network in the query of `rr_connect` (or `/machine/connect`), over plain HTTP, as Duet Web Control sends it. Without one, the bridge sends RepRapFirmware's default, `reprap`. Every other request carries the session key the board answered, in `X-Session-Key`. Neither is logged, traced, shown by `status` or `doctor`, or put in the support bundle; an error's text (which can name a request's URL) is scrubbed of the password before it is logged or shown.
- **What 3D Print Log gets** is what it gets from a Klipper printer: the file's name (without folders), times, outcome, the millimeters each tool fed (measured, not estimated), the slicer's estimate, the thumbnail, the slicer and its version and the layer height RepRapFirmware read from the file, and the firmware (RepRapFirmware and its version) and, with an SBC, DuetSoftwareFramework's version in the heartbeat. Never the board's address, unique id or password; its name (`M550`) only as the name `pair` suggests for a new printer.
- **Traces** of a Duet hold each request's path and parameters (never the password) and each answer's status and JSON body, but for `rr_connect`'s and `/machine/connect`'s (the session key left out), and of the object model only what the bridge reads (`boards`, `job`, `move`, `sbc`, `state`, `tools`, `seqs`, and of `network` only the machine's name: never its Wi-Fi network, MAC or IP addresses), never `global`. Of thumbnails, the size and position, never the image.

Tests: `test_the_bridge_logs_a_duet_print_with_measured_filament` (`tests/test_duet_adapter.py`) runs a print through the whole bridge from the fake board and checks the usage row, that only `GET` reached the board and that the password isn't in the status file; `test_a_trace_keeps_neither_the_password_nor_the_session_nor_the_network` the trace; `TestDuet` in `tests/test_privacy.py` that the password reaches no log or state file and the clock is never set.

## Anycubic (LAN mode)

With `adapter = anycubic`, the bridge connects to the printer itself, as Anycubic's slicer and Photon Workshop do in LAN mode, and to nothing of Anycubic's: no Anycubic cloud, no Anycubic account.

- **The handshake.** On each connect, `GET http://<host>:18910/info` (the printer's model, serial, whether LAN mode is on, and a one-time token), then `POST http://<host>:18910/ctrl` with an empty body and a signature made from that token. The printer answers with an encrypted login for its MQTT broker, which the bridge opens with the token: a user, a password and a device id, new each time. They live in memory for that connection only: never in a file, a log, a trace, `status`, `doctor` or the support bundle. The printer also sends a client certificate and key (the S1) or a file upload address (the P1); the bridge doesn't use them and keeps neither. The token travels in plain HTTP, as the printer hands it to anyone on your network who asks; the login is encrypted with it.
- **MQTT** over TLS to the printer's broker, at `host` (never another address the printer names) and the port `/ctrl` gives (9883 on the S1, 8883 on the P1; `mqtt_port` overrides it). The broker's certificate is self-signed, so it can't be checked: something on your network posing as the printer would get one connection's login, which only works on this printer's broker. A Photon's broker takes one client at a time: when another client (Photon Workshop) takes the connection within 30 seconds, the bridge waits 5 minutes before it asks again.
- **Requests.** Only read-only queries, each `{"type", "action", "timestamp", "msgid", "data": null}`: on an FDM printer `info`/`query`, `print`/`query`, `multiColorBox`/`getInfo` and `peripherie`/`query`, on a resin printer `status`/`query`, `lanInfo`/`query` and `print`/`query`, on connect and every 30 seconds. Anything else is refused before it is sent (`protocol.py`). It never starts, pauses, resumes or stops a print, changes a setting, a light, a fan or a temperature, turns on the camera, or lists, uploads or deletes a file.
- **What 3D Print Log gets** is the file's name (without folders), times, outcome, the filament the printer says it fed (FDM, in millimeters) or the job's resin in mL (resin), marked estimated, and the firmware version in the heartbeat. Never the printer's address, serial, device id or MAC address (but the serial and MAC address in a check-in's `discovered`), and never the login.
- **Traces** hold the bridge's queries and the printer's reports as sent, without their addresses and identifiers: `urls` (which holds a signed upload address), IP and MAC addresses, the serial (`cn`, `sn`), device and client ids, and any field naming the Wi-Fi network are dropped at any depth, and fields named like a secret are scrubbed. Never `/info`, `/ctrl` or the login.
- **Discovery.** In a scan you start in the app, and in `printlog-bridge discover` (unless `--no-anycubic`), one SSDP M-SEARCH each for `ac:3dprinter:fdm` and `ac:3dprinter:lcd`, sent to 239.255.255.250 and each scanned network's broadcast address, UDP port 1900, from an ephemeral port, with the answers read for 3 seconds. An answer names the printer's model, serial and MAC address, and its `/info` token, which is dropped.

Tests: `test_the_bridge_logs_a_kobra_s1_print` (`tests/test_anycubic_adapter.py`) runs a print through the whole bridge from the fake printer; `test_a_print_from_start_to_finish` and `test_a_resin_print_logs_its_volume` that the printer got only read-only queries; `test_a_trace_keeps_no_secret` the trace; `TestAnycubic` in `tests/test_privacy.py` that the token and the login reach no log or state file, and that only `/info` and `/ctrl` were asked over HTTP.

## The probe

`printlog-bridge probe <host>` (README, "Probing an unsupported printer") is a one-off command, not part of the running bridge. It contacts nothing but the network it runs on: no 3D Print Log, no vendor cloud, and it reads no config or key.

- **What it sends** is the allow-list in `src/printlog_bridge/probe/allowlist.py`, printed by `--help` and before each run: discovery messages (mDNS questions, an SSDP M-SEARCH, the Chitu/SDCP `M99999`), TCP connects to a fixed list of ports, and read-only status requests. Every send is checked against it first; one that isn't on it is recorded as refused, never sent, and ends only the task that tried it. It never follows a redirect, never sends credentials, never publishes on MQTT, never asks for the current file, sends nothing to port 6000 without `--photon`, and never sends a command that changes the printer's state.
- **What it records** is held only in the file it writes and the summary it prints. Datagrams from other devices on the network are counted, never recorded.
- **Redaction.** The summary always hides credentials, serial numbers, MAC addresses, Wi-Fi, host and file names, and never prints mDNS records or a Photon's answers as they came. The file holds everything unless `--redact` is given; then credentials (and passwords in URLs) become `<redacted>`; serial numbers (by field name, camelCase included, by position in a Photon's `sysinfo`, and long segments of MQTT topics), MAC addresses (with or without separators), IP addresses, Wi-Fi and host names and file names (by field name and by extension) become stable placeholders; and binary payloads are dropped. Free text such as a printer's name can still identify it: read the file before posting it.

Tests: `tests/test_probe.py` runs the probe against fake printers (HTTP, Creality and SDCP websockets, an MQTT broker, mDNS, SSDP, Chitu discovery, Bambu NOTIFY, the Photon's TCP protocol) and checks that each received only what the allow-list allows, exactly the expected requests, and that redaction leaves no serial, MAC, token, Wi-Fi name, file name or address in the file, the samples of the adversarial review of #116 included; `tests/test_privacy.py` that building the parser and `run` load nothing of the probe.

## Not covered yet

- **Pairing is off on 3D Print Log until its app lists paired bridges and lets you remove them** (3d-print-log-ui#253). Until then `pair` says so, and the bridge uses an API key, which has your account's full API access: keep it to yourself and revoke it at [3dprintlog.com/api-keys](https://www.3dprintlog.com/api-keys) if it leaks.
- **A Bambu printer is trusted on first use.** Something on your network posing as the printer the first time the bridge connects would be pinned and get the access code; `tls_fingerprint` closes that.
- **PrusaLink is plain HTTP.** Its Digest login keeps the password off the network, but the printer's answers (status, file names, the file) are readable by anyone on your network who listens, as they are for the printer's own web page.
- **An Anycubic printer's broker can't be told from an impostor**: its certificate is self-signed. Something posing as the printer on your network would get one connection's MQTT login, which works only on that printer's broker and changes every time.
- **A Duet's password crosses your network as it is**, in `rr_connect`'s query over plain HTTP, as it does from Duet Web Control.
- **OctoPrint's key crosses your network as it is** when `url` is plain HTTP, as it does from OctoPrint's own web page. Use an `https://` `url` when OctoPrint has one.
- **Traffic on your network is as secure as Moonraker's.** Remote mode talks to Moonraker over the URL you give it, usually plain HTTP on your LAN, as Mainsail and Fluidd do.
