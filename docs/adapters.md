# Writing an adapter

An adapter watches one kind of printer and reports its jobs to the bridge. Moonraker (Klipper) was the first, then Bambu Lab, PrusaLink, OctoPrint, SDCP (the Elegoo Centauri Carbon), Duet (RepRapFirmware), FlashForge (Adventurer 5M series, AD5X) and Anycubic (LAN mode); anything else with an API can follow without a change to `core/`.

For a printer whose local protocol isn't documented, start with `printlog-bridge probe <host>` (README, "Probing an unsupported printer"): one read-only trace of what it announces and answers, to work from and to turn into fixtures. Its code is in `src/printlog_bridge/probe/`; a new request it should send goes on the allow-list in `probe/allowlist.py`, with its source, and must be a read-only status query that doesn't return file names it doesn't need.

## Where things live

```
src/printlog_bridge/
  core/            printer-agnostic: config, events, API client, outbox, doctor
  adapters/
    __init__.py    ADAPTERS: the registry, by config name
    moonraker/     the Klipper adapter
    bambu/         Bambu Lab printers, over their LAN MQTT broker and FTPS
    prusalink/     Prusa printers, over PrusaLink's local HTTP API
    octoprint/     printers run by OctoPrint, over its REST API and push socket
    sdcp/          the Elegoo Centauri Carbon, over SDCP v3's local websocket
    duet/          Duet boards with RepRapFirmware, over their HTTP API (standalone or SBC)
    flashforge/    FlashForge Adventurer 5M, 5M Pro and AD5X, over their LAN HTTP API (port 8898)
    anycubic/      Anycubic printers in LAN mode (Kobra S1, Kobra 3, Photon P1), over their MQTT broker
    common/        what more than one adapter uses: MQTT, slicer settings, mDNS, resin files, timeouts
  cli/             the printlog-bridge command
```

`core/` never imports from `adapters/`. The CLI hands the registry to `core` instead, and `tests/test_layout.py` fails if anything in `core/` imports an adapter.

## Adding one

1. Create `src/printlog_bridge/adapters/<name>/` with a subclass of `printlog_bridge.core.adapter.Adapter`.
2. Add it to `ADAPTERS` in `src/printlog_bridge/adapters/__init__.py`, keyed by its `name`.
3. Users select it per printer:

   ```ini
   [printer mk4]
   adapter = prusalink
   host = mk4.local
   password = ...
   ```

## The interface

| Member | What it does |
| --- | --- |
| `name` | The value of `adapter = ...` in the config. Must match its key in `ADAPTERS`. |
| `from_config(printer, options)` | Builds the adapter from its `[printer <name>]` section, minus `adapter`. Raise `ConfigError` for anything missing or invalid, naming the section and option. Do no I/O: `doctor` loads the config before checking anything, so a printer that's off must not stop the config from loading. Reject unknown options, so a typo surfaces instead of being ignored. |
| `describe()` | One line for logs and `doctor`, such as `moonraker, remote http://u1.local:7125`. |
| `mode()`, `snapshots` | Optional, for the connection's heartbeat (#37). `mode()` returns `local` or `remote` (never the address), or `None` (the default) for an adapter without modes; `snapshots` is whether a webcam frame is added to each print, `None` (the default) for an adapter that never takes one. |
| `use_spools(spools, api_url=None)` | Optional. Called before `run` with a `SpoolSink`, for a printer that can tell which spool is in a slot: await `spools.spool_command(SpoolCommand(...))` for a user's command (naming the spool by its id, a tag, its spool number, or a `SpoolmanSpool` in the user's own Spoolman) (it returns the answer to show them, and never raises) and `spools.spool_reading(SpoolReading(...))` for what a reader in a slot sees. Don't wait on either in your connection's read loop. `spools.watch_loaded(printer, watcher)`, when the sink has it (look it up with `getattr`), tells `watcher` each slot's spool, `spoolNumber` included, now and after each change, and returns what stops that; the watcher must not block. `api_url` is the bridge's 3D Print Log API URL, for deciding whether the printer's own spool server is 3D Print Log (the Moonraker adapter syncs Moonraker's Spoolman active spool both ways only when its server's host is `api_url`'s, and follows any other server one way). The bridge passes both, so an override must accept `api_url` too. |
| `use_trace(trace)` | Optional. Called before `run` when `trace = true`, with the printer's `Trace` (`core/trace.py`): call `trace.record(SEND, raw)` and `trace.record(RECEIVE, raw)` with each message's JSON text as it goes out and comes in, and `trace.mark("open")` / `trace.mark("close")` around each connection. Neither waits or raises; the trace scrubs secrets and writes in a thread of its own. |
| `use_state(state)` | Optional. Called before `run` with the printer's `PrinterState` (`core/state.py`), for an adapter that keeps something of its own between runs: put it in `state.discovery` (plain JSON, never a password) and call `state.save()`. The Moonraker adapter keeps the printer's identity and last found address there (`adapters/moonraker/locator.py`). |
| `serves(path)` | Optional, for `doctor`'s check of where the API key is kept. When the software on the printer's host serves `path`'s folder to its users (Moonraker its `config`, `gcodes` and `logs`; OctoPrint `~/.octoprint/uploads`), return who can download it, in words that follow "which" and "a folder": `Moonraker serves to anyone who can open Mainsail or Fluidd`. Otherwise `None`, the default. Look at the local file system only: `doctor` asks every configured printer's adapter about the config file and the key file. |
| `discovery()` | Optional classmethod: the adapter's discovery hook, a `core.discovery.Discovery` (see [Discovery](#discovery)), or `None` (the default) when its printers can't be found on the network. |
| `app_options(host, port, serial, secrets)`, `app_secrets` | Optional classmethod, for a printer the user connects in the app (#100): the `from_config` options to watch it at `host` (an IP address the bridge resolved and checked is private), or `None` (the default) when the adapter can't be set up that way. `secrets` holds its credentials, opened from the app (sealed to the bridge, `core/credentials.py`) or from its `[app_printer <id>]` section, which wins; `app_secrets` names them (`access_code`, `password`...), the same names as 3D Print Log's `secretFields`. Raise `NeedsCredentials("what to add", fields=("access_code",))` when one is missing: the bridge waits for it, says so, and reports `fields` as `missing`. `from_config` must use credentials as given, without trimming: one opened from the app is used exactly as it opened. When the printer refuses them, call `report.credentials_refused(fields)` with the options it sent (`connected()` clears it), so one from the app is reported as `rejected_by_printer`. |
| `watches(found)`, `found_entry()` | Optional, no I/O. `watches` says whether a `Found` printer is the one this config-file printer watches (by serial, MAC, or address and port), so it is reported as `configured` and wins over the app; `found_entry` is this config-file printer as a check-in reports it, when its address is known. |
| `check()` | Diagnostics for `doctor`: a list of `CheckResult`s named `Printer <name>`. Return `fail` when the bridge can't work (unreachable, wrong credentials), `warn` when it can but something needs attention (Klipper shut down). Don't raise; `doctor` reports an exception as a failed check, but your message will be better. |
| `run(sink, report)` | Watches the printer until cancelled, awaiting `sink.emit(event)` for each job event, in order. Reconnect on your own after a dropped connection, and after each connect replay every job that started at or after `await sink.resume_after(printer)` (or, when that is `None`, only a job running now). Tell `report` (a `PrinterReport`) what `printlog-bridge status` should show: `connected()`, `disconnected(reason)`, `printer_state(state)` for the printer's own state, and `warn(topic, message)` for something the user must fix, cleared with `warn(topic, None)` once it's fixed. The heartbeat also sends what you give `firmware(name, version)` (what runs the printer: `Klipper`, `Prusa-Firmware-Buddy`), `host_software(name, version)` (what you talk to on the printer's host: `Moonraker`, `PrusaLink`; never call it for a printer you talk to directly) and `printer_model(model)` (the model the slicer wrote in a job's file), so never pass any of them a host name or anything else the user typed. Call them as soon as you know, after each connect: until then the heartbeat leaves the fields out, and 3D Print Log keeps what it had. Warnings and errors you log starting `[printer <name>]` are counted for that printer's heartbeat. Return only when cancelled. |

## Events

Adapters report jobs with the types in `printlog_bridge.core.events`, never with their printer's own vocabulary.

- `JobStarted(printer, job_id, file_name, started_at, estimated_duration_s, estimated_filament_mm, estimated_filament_g, estimated_filament_g_by_slot, estimated_volume_ml)`, the estimates from the slicer when the file has them. `estimated_filament_g_by_slot` maps slot to grams, only for a file with a weight per tool; leave it empty otherwise and the totals make one row. `estimated_volume_ml` is a resin printer's: the slicer's resin in milliliters, on slot 0 (see below).
- `JobFinished(printer, job_id, outcome, finished_at, duration_s, filament_mm, filament_g, usage_estimated, note, volume_ml)`, where `outcome` is a `JobOutcome` (`COMPLETED`, `CANCELLED` or `FAILED`), `filament_mm` maps slot index (tool 0, 1, ...) to millimetres fed (one entry, slot 0, on a single-tool printer; a slot that fed nothing can be left out), `filament_g` maps slot index to grams, for a printer that reports weight (a Bambu 3MF's `used_g` per filament), `usage_estimated` is `True` when both are the slicer's estimate rather than what the printer measured (see below), and `note` says in words for the print's notes why a job failed ("Klipper shutdown"), or anything else worth knowing about how it went ("2 of 6 objects were cancelled: PART_3, PART_5").

  A slot with grams is sent by weight (`amountMg`, `source: 1`) and keeps its millimetres beside them when it has both; a slot with millimetres only is sent by length (`lengthInM`, `source: 2`). Klipper and RepRapFirmware measure what they fed, so the Moonraker and Duet adapters send `filament_mm` and leave `usage_estimated` off. Most other firmwares (PrusaLink, Bambu, OctoPrint) report only the slicer's estimate and how far the job got: send that estimate (for a job that didn't finish, scaled by its progress if you like) with `usage_estimated=True`, and every row gets `actualIsEstimate: true`. 3D Print Log still charges the spools, but leaves those rows out of its accuracy analytics, which would otherwise compare the estimate with itself. Report every slot the same way: a spool on two slots, one weighed and one measured, keeps only what both have.

  **Resin (#97).** A resin printer is a printer with one slot in 3D Print Log: its vat is slot 0, and the bottle loaded on it is that slot's spool. Report its usage as `volume_ml={0: <mL>}` (and the start's estimate as `estimated_volume_ml`), with no `filament_mm` or `filament_g`. A slot with a volume is sent by volume, whatever else it has: the estimate row as `{"slot": 0, "estimatedVolumeMl": 40.0, "estimatedSource": 3}` (with `filament: {id}` when a bottle is loaded), and the end as `{"slot": 0, "volumeMl": 42.5, "source": 3, "actualIsEstimate": true}` (with `filamentId` when a bottle is loaded). Every volume row is marked an estimate, `usage_estimated` or not: it is always the slicer's figure. Volumes are rounded to 0.01 mL. A job with no volume (say, a file the adapter couldn't read) still logs, with no usage rows. For a job that didn't finish, scale the volume by the layers printed over the layer count. `adapters/common/resin_files.py` reads the volume, layer count and print time from the start of the job's file (`read_resin_file(data)`, `HEADER_BYTES` of it): Chitu `.ctb`/`.cbddlp`/`.photon` (not Chitubox's encrypted CTB), Elegoo `.goo` and Anycubic Photon Workshop files (`.pwmx`, `.pws`, `.pwma` and the rest); its docstring has the layouts. A bottle swapped mid-print is split by `JobPoint.progress`, so give `progress` and a `fed_mm` for slot 0 above 1 (the height printed so far in mm will do) once the job has begun.
- `JobImage(printer, job_id, kind, fetch)`, a picture of the job: `ImageKind.THUMBNAIL` (the slicer's preview) after the job's start, `ImageKind.SNAPSHOT` (a webcam frame) after its finish. `fetch()` returns the image's bytes, or `None` when there is none; the sink calls it only when it still wants that picture, so a replay costs nothing. Give up within 10 s and raise `ImageUnavailable` (`core/images.py`) with a message that is safe to log; `fetch_image` and `read_image_file` there already bound size and time and mask passwords in URLs. The sink stops waiting after 15 s regardless, and a picture never holds up its print: one that can't be had is skipped, and one the API refuses is dropped.
- `JobAttachment(printer, job_id, kind, file_name, fetch)`, a file to attach to the job's print, a Pro feature: `AttachmentKind.TIMELAPSE` (the job's timelapse video), any time after its finish. `file_name` is the name it gets in 3D Print Log. `fetch(path, max_bytes)` writes the file to `path` and returns `True`, or returns `False` when there is none; raise `FileUnavailable` (`core/images.py`) with a message safe to log when it can't be had or is over `max_bytes`, and leave no file behind. `download_file` and `copy_file` there stream it to disk within those limits. The sink calls it only for an account with Pro, once per job and kind, and stops waiting after 10 minutes. Don't await `emit` for it from the code that reads the printer's news: the fetch takes a while. Only an MP4 is attached for now.

- `JobSlicerSettings(printer, job_id, metadata, read)`, the slicer settings of the job's file, after its start (and after its thumbnail). Whatever the file is, `read()` returns the text shape below, since that is what 3D Print Log parses: for a binary `.bgcode` (Prusa's default) or a 3MF (Bambu), turn the settings into a `; key = value` block with `config_block_from_settings(settings)` (`core/slicer_settings.py`) from the bgcode file's slicer metadata block or the 3MF's `Metadata/project_settings.config`, leave `header` out (the slicer and its version go in `metadata`), and read only those parts of the file. `metadata` is a `SlicerMetadata` from what the printer already knows of the file (the slicer, its version, layer heights, nozzle, filament, first layer temperatures), or `None`. `read()` returns a `SlicerFile(header, config_block)`: the start of the file through `; HEADER_BLOCK_END` (PrusaSlicer: its first line) and the `; key = value` block after the G-code, as read, or `None` when neither can be had. `header_from` and `config_block_from` (`core/slicer_settings.py`) cut them from the bytes read. Never read the toolpaths: read byte ranges, as `fetch_range` and `read_range` (`core/images.py`) do. Don't read the file before the sink calls `read`: it never does with `slicer_settings = false`, and only once per job. The sink scrubs hosts and credentials, stops waiting after 15 s, and sends the metadata alone when `read` fails.

- `FilamentChange(printer, slot, at, reason)`, a job paused for a filament change (`reason` is `runout` or `unload`) that has resumed, where `at` is the `JobPoint` it was paused at. When no spool was assigned to that slot at that point, the print gets a note saying how to split its usage next time.

- `SpoolCommand(printer, slot, filament_id, tag, slot_count, during)`, the user assigning a spool to a slot by its id in 3D Print Log or a tag's UID, or clearing the slot (neither). `slot_count` is how many tools the printer has, when you know; a slot beyond what 3D Print Log has makes it add slots, up to that.
- `SpoolReading(printer, slot, tag, material, color_hex, slot_count, during)`, what a reader in a slot sees: a tag's UID as hex, the material it names (`PLA`), its color as `#RRGGBB`. Report a slot when its reading changes, and an empty reading when the spool is gone: that forgets the slot's lookup, so a spool put back is looked up again at once. A tag one of the user's spools has assigns that spool; one that no material has is looked up again every `UNKNOWN_TAG_RETRY_S` (5 minutes) by `Spools.run`, at most once per slot in that time, so you don't need to report it again; otherwise a material or color unlike the assigned spool's adds a note to the print.

Give both a `during` while a job runs: a `JobPoint(job_id, fed_mm, progress, layer)` taken when you heard of the command or reading, with `fed_mm` the millimetres each slot has fed so far on the scale of `JobFinished.filament_mm`. A printer that only weighs can't measure that: give an estimate (the slicer's length for the slot times the job's progress), since a swap before the slot fed 1 mm counts as the slot's spool from the start, and give `progress`, which is where a slot with grams but no millimetres is split. A spool that then changes in that job's slot splits the slot's usage there (#44): the part before goes to the old spool and the rest to the new one, kept in the job's state so a restart doesn't lose it, and the print gets a note such as "T0: Spool A → Spool B at 63% (layer 112)". Leave it `None` between jobs. A spool assigned before its slot fed anything (1 mm) is the slot's spool from the start, not a split. The job's end is worked out once (rows and notes, kept in its state) and sent the same way on every retry, so a slot already split on the print is never counted twice. A print only created after a swap (3D Print Log was unreachable) starts with the spool the slot started with.

`job_id` must be stable for the job's lifetime and unique on that printer, such as Moonraker's history `job_id`. The sink (`core/lifecycle.py`) writes each event to the outbox (`core/outbox.py`, SQLite in the state directory) and returns without waiting on the API, then sends it from there; so `emit` is quick even while 3D Print Log is unreachable. It logs a job under `<instance>:<job_id>`, where the instance id is a UUID kept in the state directory per printer, and remembers each job it has logged, so a replayed event is recognised instead of logged twice. Replays are expected: emit a job's start again before its finish whenever you aren't sure the start was seen.

Use timezone-aware `datetime`s.

## Printers without job history

`run` replays jobs from `resume_after` after each connect, which needs the printer to keep a job history, as Moonraker does (`server.history`). PrusaLink, Bambu's local API, OctoPrint's core, SDCP, RepRapFirmware, FlashForge's LAN API and Anycubic's LAN mode say only what is printing now. For those, `core/current_job.py` keeps the running job in the printer's state (`state.discovery["current_job"]`, so take the `PrinterState` in `use_state`):

- `CurrentJob(state)` (with `MemoryState()` from `core/state.py` for a printer the bridge gives no state, one without a `printer_id`), then `started(event)` when you emit a `JobStarted`, `seen()` now and then while it runs (written at most once a minute), and `ended()` once you have emitted its `JobFinished` yourself.
- After each connect, emit every event `reconcile(running, outcome=None, finished_at=None)` returns, where `running` is the `job_id` the printer is running now (or `None`), and `outcome` and `finished_at` are what the printer says of how and when its last job ended, when it says. The same job still running gives its start again, which the sink recognizes. Another job, or none, gives the remembered job's start and its `JobFinished`: the printer's outcome, or `COMPLETED` when it doesn't say; the printer's end time, or when the bridge last saw the job running, with a note on the print saying so. A job taken as complete carries the slicer's estimate as its usage, marked estimated. Then it is forgotten, so it is never finished twice.

**A job that starts and ends entirely while the bridge is down (or the printer is unreachable) is missed**: nothing on the printer says it ran. Neither is a job that ended while the bridge was away told from one cancelled at once, unless the printer reports how its last job ended. Say so in the adapter's setup docs.

`job_id` must still be stable and unique: when the printer gives no id of its own, make one from what it does give, such as the file name and the start time.

## Discovery

While the bridge runs with a device token that has `bridge:sync`, it looks for printers on the network and reports the ones an adapter recognizes to 3D Print Log, for "Found on your network" (`core/discovery.py`, #100). It never watches one because it found it: the user connects it in the app, and the bridge hears that from its desired list (`core/bridge_sync.py`, `core/app_printers.py`). An adapter takes part through its hook, a subclass of `Discovery`:

| Member | What it does |
| --- | --- |
| `kind` | The adapter's name, which is the check-in's `kind`: `moonraker`, `bambu`, `prusalink`, `octoprint`, `sdcp`, `duet`, `flashforge`, `anycubic`. |
| `mdns_services`, `from_mdns(answer)` | The mDNS service types its printers advertise (`_moonraker._tcp.local`), and the printer behind an answer (`core.mdns.MdnsAnswer`: instance name, host, address, port, TXT), or `None` when it isn't one. It may ask the printer, briefly, without a key. One query for every adapter's types goes out every 5 minutes, from an ephemeral port (nothing binds 5353). |
| `udp_ports`, `from_datagram(port, data, sender)` | UDP ports to listen on for announcements (Bambu's NOTIFY on 2021), and the printer that sent `data`, or `None`. No I/O. |
| `sweep(networks)` | Every printer of this kind on `networks` (private /24s). Runs only when the user taps "Scan now" in the app, at most once a minute: a sweep looks like a port scan to network security tools. |

Return a `Found(kind, address, port, model, name, serial, mainboard_id, macs)` with what identifies the printer best (a serial, a mainboard id, the host's MACs), since 3D Print Log tells printers apart by it. The service keeps only private addresses, cleans every field to the API's rules, keeps at most 50 printers, merges the same printer seen twice, and forgets one not seen for 30 minutes (24 hours when only a sweep found it). Code more than one adapter uses lives in `adapters/common/` (mDNS answers, slicer settings), never imported from another adapter. A kind with no adapter isn't reported: the app would offer to connect a printer no bridge can watch. `tests/test_lan_discovery.py` covers the hooks and the service; `tests/test_bridge_sync.py` the check-in against the fake API's bridge endpoints, and `tests/test_app_printers.py` the whole bridge applying a desired list.

## Tests

Test against a real local server rather than mocking your HTTP client, and make that server behave like the real printer, checked against one. `tests/fake_moonraker.py` speaks Moonraker's JSON-RPC over a WebSocket and over its Unix socket, including its authorization and its one-agent-per-name rule. `tests/test_moonraker_adapter.py` covers config parsing and each `check()` outcome; `tests/test_moonraker_session.py` covers the connection, reconnects and Klipper restarts; `tests/test_moonraker_jobs.py` covers turning history into events. `tests/fake_printlog_api.py` stands in for the 3D Print Log API with its rules for connectors (idempotent create, complete, patch), and `tests/test_job_lifecycle.py` runs the whole bridge between the two fakes, including a print made with the API unreachable (`api.offline = True` cuts every request off). `tests/test_outbox.py` covers the outbox on its own, and `tests/test_job_logger.py` covers sending from it: order per print, backoff, `Retry-After`, a power cut in the middle of a send, the 30-day limit, and pictures; `tests/test_moonraker_images.py` covers finding a job's thumbnail and webcam snapshot, against `tests/fake_webcam.py`. `tests/test_moonraker_slicer.py` reads real slicer files' header and settings block by range from the fake (which serves `Range` as Moonraker does), `tests/test_slicer_settings.py` covers the scrubbing and the request body, and `tests/test_slicer_settings_logging.py` sending them against the fake API's endpoint. `tests/test_spools.py` covers assigning spools and slot readings against the fake API's slot and tag rules, `tests/test_moonraker_spools.py` the console commands and the U1's reader, `tests/test_macros.py` renders `klipper/printlog.cfg` with jinja2 as Klipper does, and `tests/test_spool_assignment.py` runs it all through the bridge.

A fake is only as good as its likeness, so `tests/integration/` checks it. `test_fake_matches_moonraker.py` sends the same raw JSON-RPC exchanges to the fake and to a real Moonraker in Docker and expects the same answers, and `test_real_moonraker.py` runs the bridge itself against the real one: auth, the extensions list, a second bridge, a Moonraker restart, and local mode inside the container. When you learn something new about Moonraker, add it to both the fake and the contract test.

## The Moonraker adapter

`adapters/moonraker/session.py` keeps one JSON-RPC connection open: the Unix socket in local mode (each message ends with an ETX byte, `0x03`), `ws://<printer>/websocket` in remote mode. On each connect it identifies as an agent, registers its remote methods (none yet), and subscribes to `print_stats`, `toolhead.extruder` and `toolhead.position`, `virtual_sdcard`, `webhooks`, `filament_detected` and `enabled` of every runout sensor (`filament_switch_sensor <name>`, `filament_motion_sensor <name>`) and, when the printer has it, `filament_detect`. It subscribes again after every `notify_klippy_ready`, and reconnects with a backoff that doubles from 1 s to 60 s and resets after a good connection. `check()` asks `server.info` over that same connection, without identifying, so `doctor` tests the path `run` uses.

`adapters/moonraker/notifier.py` reads `server.config` on every connect, and in `check()`, for `[notifier ...]` sections whose `url` posts to `3dprintlog.com` or a host under it: the older way of logging prints, which would log each one twice beside the bridge. While one is there, it's a warning naming the section and its file (from `server.config`'s `files`), never the URL, which holds the user's API key. Moonraker reads its config only when it starts, so the reconnect after the restart that removes the section clears the warning. A config that can't be read changes nothing.

`adapters/moonraker/jobs.py` turns job history into events. `notify_history_changed` reports a job when it is added and when it finishes, and on every connect `server.history.list` is read from the resume point, a page at a time, so a job that started or ended while the bridge was away is still reported. A job Moonraker found in progress when it started is `interrupted`, and is only ever seen this way. For an `error`, the note carries `print_stats.message` when the bridge saw it. While a job is in progress, `JobTracker.point()` says how far it has got (`print_stats.filament_used` split by tool as `tools.py` does, `virtual_sdcard.progress`, `print_stats.info.current_layer`), which `SpoolWatcher` puts on each spool command and reading.

`adapters/moonraker/changes.py` notices a pause for a filament change (#44): a runout sensor's `filament_detected` going from true to false while a job runs and the job pausing within 200 mm of feed after it with the sensor still empty, or the extruder (`toolhead.position[3]`) going back 25 mm or more while it's paused, as an `M600` unload does (Klipper's `filament_used` stands still while paused, so the unload isn't counted; a tool change resets the count, since the position becomes the other extruder's). It asks on the console for the new spool with `_PRINTLOG_RESPOND` when `printlog.cfg` is included, once the job has paused, and reports a `FilamentChange` when the job resumes. A sensor named for a tool (the Snapmaker U1's `filament_motion_sensor e0_filament` to `e3_filament`) is that tool's; any other is the active tool's.

`adapters/moonraker/slicer.py` reads a job's slicer settings. Moonraker's file metadata (which the history entry carries, or `server.files.metadata` gives) has `size`, `gcode_start_byte` and `gcode_end_byte`: the header is read from the start of the file up to `gcode_start_byte` (at most 64 KB), and the settings block from one byte before `gcode_end_byte` to the end (at most the last 512 KB), dropping the first line read, since Moonraker v0.9.3 and older count `gcode_end_byte` in characters (`gcode_metadata(data, moonraker="v0.9.3")` in the fake reproduces that), with a `Range` request to `/server/files/gcodes/<path>` in remote mode and from the gcodes folder in local mode. The summary comes from the metadata's `slicer`, `slicer_version`, `layer_height`, `first_layer_height`, `nozzle_diameter`, `filament_name`, `filament_type`, `first_layer_extr_temp` and `first_layer_bed_temp` (the API has no fields for `chamber_temp`, `layer_count` or `object_height`).

`adapters/moonraker/tools.py` splits a job's filament by tool. Klipper counts one total per print (`print_stats.filament_used`, across every extruder), and neither its extruder objects nor Moonraker's history entry (`filament_used`, `auxiliary_data`) say how much each tool fed. So `ToolUsage` gives each increase of the total to the extruder named in `toolhead.extruder` at that status update (`extruder` is slot 0, `extruder<N>` slot N), and restarts when Klipper loads a new file. At the job's end, `per_slot` scales what it saw to the history entry's `filament_used`, which stays the source of truth; with nothing seen (the job ran while the bridge was away), it splits by the slicer's grams per tool (`filament_weights` in the file's metadata, one per filament in tool order, from PrusaSlicer, OrcaSlicer and Snapmaker Orca), and with neither it's all slot 0. An MMU print on one extruder (`mmu_print`) has no per-tool estimate: its filaments are gates, not tools. Without `[history]` in moonraker.conf the history methods don't exist, and the bridge logs how to turn it on.

`adapters/moonraker/spools.py` takes spool commands from the console. The `PRINTLOG_SET_SPOOL` and `PRINTLOG_CLEAR_SPOOL` macros (`klipper/printlog.cfg`) print a line such as `// printlog: SET_SPOOL TOOL=2 TAG=04A23F11` with `action_respond_info`, Moonraker sends every console line to every client as `notify_gcode_response`, and `SpoolWatcher` passes the command on and shows the answer with the file's `_PRINTLOG_RESPOND` macro (through `printer.gcode.script`). Not `action_call_remote_method`: Klipper raises an error when no client has registered the method, so with the bridge restarting or offline the macro would fail, and in a print's G-code that ends the print. A console line can't fail; the cost is that one printed while the bridge is away is missed, which the macro tells the user to look out for.

`adapters/moonraker/spoolman.py` keeps Moonraker's Spoolman active spool and the tool slots in 3D Print Log in step, when `[spoolman] server` is 3D Print Log (its host, case-insensitively and without userinfo or port, is the host of `api_url`; another server is the user's own, below). On every connect it reads `[spoolman] server` from `server.config`, then the active spool with `server.spoolman.get_spool_id`. Moonraker announces a pick as the `notify_active_spool_set` notification (`[{"spool_id": <int|null>}]`, which `session.py` routes to listeners that ask for it); the bridge looks the number up with `GET /api/Filaments/by-number/{n}` and loads it into the active tool's slot through the same `SpoolSink.spool_command` as the console macros, so a pick during a print is a swap. A null id changes nothing, and an unknown number is logged and dropped, with no retry and nothing queued. The other way, a tool change (`toolhead.extruder`) or a new spool in the active slot (`Spools.watch_loaded`) calls `server.spoolman.post_spool_id` with `{"spool_id": <number>}`; an empty slot or a spool with no number posts nothing. Nothing read is written back, and the notification answering the bridge's own post isn't taken for a pick. On connect it posts only when the job isn't printing or paused. A Moonraker without the spoolman component answers these methods with method-not-found, which is logged once at debug and ignored.

With any other `[spoolman] server`, the user's own Spoolman (#38), `spoolman.py` follows it one way and writes nothing: no `post_spool_id`, and only `GET` requests through Moonraker's proxy. The spool each slot gets is either the tool's own, when the printer's macros keep one per tool (the `spool_id` variable of `gcode_macro T<n>`, which Fluidd and Mainsail set, or `t<n>__spool_id` in `save_variables`; the session subscribes to both, but only to tool macros of extruders Klipper has, since the U1 defines T4 to T31 for its four tools), or else Moonraker's active spool for the active tool. A per-tool spool makes the active spool, which tool change macros set from it, ignored. Each spool is read with `server.spoolman.proxy` (`{"request_method": "GET", "path": "/v1/spool/<id>", "use_v2_response": true}`; an older Moonraker answers with Spoolman's body alone, which is read too) and passed on as `SpoolCommand(spoolman=SpoolmanSpool(id, name, tags))`, `tags` being the spool's `nfc_id` extra field, JSON-decoded. `Spools` asks `GET /api/Filaments/by-spoolman-id/{id}`, then `GET /api/Filaments/by-tag/{uid}` for each tag, and with no material answers with a hint. A spool Spoolman can't describe is looked up by its id alone. On connect it assigns the spools active then, unless a print is running or paused, and only those that changed since this bridge last saw them, so a reconnect or a Klipper restart assigns nothing again.

`adapters/moonraker/u1_rfid.py` reads the Snapmaker U1's RFID reader, Klipper's `filament_detect` object, written from Snapmaker's published firmware (`u1-klipper`'s `filament_detect.py` and `filament_protocol.py`) and checked against a real U1's answers (`tests/fixtures/moonraker/u1`, `tests/test_real_captures.py`). `info` has one entry per channel, channel `n` feeding `extruder<n>`; an entry is filled in only for a Snapmaker tag whose signature checked out (`VENDOR` is `NONE` otherwise), with `CARD_UID` as a list of byte values, `MAIN_TYPE` the material and `RGB_1` the color. Confirmed on a U1 (Klipper 2.0.0.205, Moonraker 2.0.0): `filament_detect` is in `printer.objects.list`; `CARD_UID` is a list of four bytes (`[160, 93, 28, 63]`), and the number `0` in an empty slot, whose `VENDOR` is `NONE`; `RGB_1` is the color the slicer has for the same spool. Still to check, with a trace (`trace = true`): that the status arrives through a subscription while printing, that the byte order is the one a phone's NFC app shows, and how an entry changes when a spool is pulled out or runs out.

## The Bambu adapter

`adapters/bambu/` watches a Bambu Lab printer (X1, P1, A1, H2) over its LAN connection. **It is built from documentation, not from a recorded printer**: OpenBambuAPI (`mqtt.md`, `tls.md`), ha-bambulab's `pybambu` (`bambu_client.py`, `models.py`), and Bambu's wiki on LAN Only Mode and Developer Mode (Oct 2026). `tests/fake_bambu.py` follows the same sources. Replace its reports with a real trace (`trace = true`, #17) when one exists, and check each point below against it.

- **`common/mqtt.py`** (shared with the Anycubic adapter): the five packets of MQTT 3.1.1 the bridge needs (CONNECT, SUBSCRIBE, PUBLISH at QoS 0, PINGREQ, DISCONNECT) on asyncio streams, so there is no dependency to build for every platform the image is made for, and no thread. User `bblp`, the access code as password, a clean session, keepalive 60 s. A CONNACK other than 0 is `MqttRefused`, which `check()` and `run` turn into the access code and Developer Mode message.
- **`tls.py`**: the printer's certificate is issued by one of Bambu's own CAs (a new one with several model generations) with the serial as its name. The chain isn't verified; the certificate is pinned on first use per service (`state.discovery["bambu_certificates"]`), and a different one is refused before the access code is sent. `tls_fingerprint` pins MQTT's by hand. TLS 1.2 at most, as ha-bambulab.
- **`jobs.py`**: reports (`{"print": {...}}` on `device/<serial>/report`) are merged into one status, since a P1 or A1 sends only what changed; on each connect the bridge asks for `get_version` (the `ota` module's `sw_ver` is the firmware) and `pushall` (the whole status; again every 30 minutes, never more often, as it loads a P1P). `gcode_state` drives the job: it starts at `RUNNING` (or `PAUSE`, or an end before either), with `started_at` from `gcode_start_time`, and ends at `FINISH` (completed), `FAILED` (cancelled when `print_error` is 0x0300400C or 0x0500400E, failed otherwise with the code in the note) or `IDLE` straight from a running state (cancelled, with a note). `job_id` is `<gcode_start_time>-<subtask_name>`, since `task_id` is 0 for a print that didn't go through the cloud. With no history, `CurrentJob` keeps the running job, and the first whole status after each connect is reconciled: the printer's `FINISH` or `FAILED` is the remembered job's outcome only when its `gcode_start_time` and name are the remembered job's.
- **`ftps.py`, `files.py`, `threemf.py`**: the job's 3MF is fetched whole over implicit FTPS (port 990, PROT P, data connections on the control connection's TLS session) when the job starts printing, into a temporary file kept until the next job. It is looked for as `/cache/<subtask_name>.3mf` (cloud and MakerWorld prints), `/<subtask_name>.gcode.3mf` and the file `gcode_file` names (LAN and SD prints); `gcode_file` under `/data/` is the printer's RAM disk and is skipped. From it the bridge reads `Metadata/slice_info.config` (the plate's `prediction`, `weight`, and each filament's `used_g` and `used_m`), `Metadata/plate_<n>.png` (the thumbnail) and, only when the sink asks, `Metadata/project_settings.config` (JSON, turned into a settings block with `config_block_from_settings`). The plate is the one `gcode_file` names (`plate_<n>.gcode`), else `plate_idx`, else the only plate.
- **`slots.py`**: slot 0 is the external spool (`vt_tray`, id 254), 1-16 the trays of AMS units 0-3 (`1 + 4 * ams + tray`), 17-24 AMS HT units 128-135, 25 the H2D's second external spool (255). A filament's tray comes from `ams_mapping` (`ams * 4 + tray` per filament) or `ams_mapping2`, else the loaded tray (`tray_now`) for a one-filament job, else filament N on tray N. Each tray's `tag_uid` (not all zeros), `tray_type` and `tray_color` go to `SpoolReading` when they change, with a `JobPoint` while a job runs whose `fed_mm` is the slicer's length times `mc_percent`.
- **`discovery.py`**: `printlog-bridge discover` listens 6 s on UDP 2021 for the printers' `NOTIFY` announcements (`Location`, `USN`, `DevModel.bambu.com`, `DevName.bambu.com`). `run` never listens.

To check on a real printer: the field names and states above on each model and firmware; whether `pushall` and `get_version` are answered without Developer Mode; the cancel codes; whether `print_error` arrives before or with `FAILED`; `ams_mapping` for an AMS HT and the H2D; whether FTPS works without Developer Mode; and whether the FTPS certificate is the MQTT one. Tests: `tests/test_bambu_mqtt.py` (the client and the pin), `test_bambu_files.py` (FTPS and the 3MF), `test_bambu_slots.py`, `test_bambu_jobs.py` (the lifecycle and reconnects), `test_bambu_adapter.py` (config, `check()`, `run`, and the whole bridge against the fake API), `test_bambu_discovery.py`.

## The PrusaLink adapter

`adapters/prusalink/` watches a Prusa printer with PrusaLink built in (Prusa-Firmware-Buddy: MK4/MK4S, MK3.5/3.9, Core One, MINI, XL), and should also work with PrusaLink on a Raspberry Pi (an MK3S). **It is built from Prusa's published sources, not a recorded printer**: Prusa-Link-Web's `spec/openapi.yaml`, Prusa-Firmware-Buddy's `lib/WUI/link_content/` (`prusa_link_api_v1.cpp`, `basic_gets.cpp`, `usb_files.cpp`, `previews.cpp`), `lib/WUI/nhttp/` (`req_parser.cpp`, `status_page.cpp`, `status_renderer.cpp`, `file_info.cpp`, `send_file.cpp`) and `src/state/printer_state.cpp`, and libbgcode's `doc/specifications.md` (Oct 2026). `tests/fake_prusalink.py` follows the same sources. Replace it with a real trace (`trace = true`, #17) when one exists, and check each point below against it.

- **`client.py`**: GET only, on aiohttp. Buddy asks for HTTP Digest, user `maker`, realm `Printer API`, without `qop` (so RFC 2069's MD5(HA1:nonce:HA2)), with a nonce good for 300 s and `stale=true` after; it also takes the password as `X-Api-Key`, and older firmware asks only for that (`WWW-Authenticate: ApiKey`). aiohttp has Digest only from 3.12, so the client answers the challenge itself, `qop=auth` included when offered, and reuses the nonce, so a poll is one request. A second refusal for a fresh nonce is `Refused`.
- **`jobs.py`**: `/api/v1/status` is polled (`poll_interval`, 5 s, while a job is under way; `idle_poll_interval`, 30 s, otherwise). Buddy reports `job` only while it is `PRINTING`, `PAUSED` or `ATTENTION` in a print, and ends at `FINISHED` or `STOPPED` (without `job`), which stays until dismissed on the screen, or `ERROR`. A job starts when first seen `PRINTING` or `PAUSED`, with `started_at` now less `time_printing`, and ends `COMPLETED`, `CANCELLED` or `FAILED` (with `status_printer.message` when the printer gives one); gone with the printer back at `IDLE` or `READY` it is taken as completed at 99% or more, else cancelled, with a note. `BUSY` or `ATTENTION` without a job (crash recovery, a power panic) doesn't end it. `job_id` is `<job id>-<file name>`, the printer's counter alone repeating after a reset. `CurrentJob` keeps the running job; after each connect, `FINISHED`, `STOPPED` or `ERROR` is taken as the remembered job's outcome (it can't be checked: the job is gone from the status by then).
- **`files.py`, `bgcode.py`**: `/api/v1/job` once per job. PrusaLink on a Pi puts the file's metadata in `file.meta`; Buddy gives only `refs` (`download` is the file's short path under `/usb/`, `thumbnail` under `/thumb/l/`) and serves files without `Range`. So a `.bgcode` file (or `.bgc`, its short name) is streamed until `BgcodeReader` reaches the first G-code block (at most 8 MB), and a plain `.gcode` file is streamed whole (at most `DEFAULT_MAX_GCODE_BYTES`, 64 MB, by the job's `file.size`; 180 s) keeping its first 64 KB and last 512 KB. Estimates are PrusaSlicer's `filament used [g]` and `[mm]` (comma-separated per tool) and `estimated printing time (normal mode)` from the printer and print metadata blocks, or the comments after the G-code; tool N is slot N, tools at 0 left out. A bgcode metadata block may be stored, deflated (zlib, or raw Deflate) or Heatshrink-compressed (window 11 or 12, lookahead 4); one in another compression or encoding is skipped and logged. The slicer metadata block becomes `config_block_from_settings`; the slicer and its version come from the file metadata's `Producer`. The thumbnail is the largest PNG or JPEG block, else the printer's `refs.thumbnail`.
- **`adapter.py`**: config (`host`, `port`, `username`, `password` or `api_key`, `poll_interval` at least 1 s, `idle_poll_interval` at least `poll_interval`, `files`), `/api/version` once per connect (Buddy: firmware `Prusa-Firmware-Buddy` and its `firmware`, host software `PrusaLink` and `api`; a Pi: `Prusa-Firmware` and PrusaLink's `version`), a 404 from `/api/v1/status` taken as firmware too old for the v1 API, and `check()` for `doctor`. Backoff 5 s doubling to 60 s while unreachable, 5 minutes after refused credentials.
- **Discovery**: not yet. Buddy firmware can answer mDNS, and `/api/version` answers 401 with `realm="Printer API"`, so a probe could be added to `discover` (#100).

To check on a real printer: the field names and states above on each model and firmware; whether `FINISHED`/`STOPPED` stay until dismissed when the printer is also on Prusa Connect; what `status` and `job` say on an XL and with an MMU3; the menu path to the password on each model; the minimum firmware with `/api/v1/`; whether the file download stops cleanly mid-print; files sliced in PrusaSlicer's window, which have thumbnails. Tests: `tests/test_prusalink_client.py` (Digest, stale nonces, the key), `test_prusalink_bgcode.py` (two real PrusaSlicer 2.9.2 files in `tests/fixtures/gcode/`, blocks, every compression, Heatshrink), `test_prusalink_files.py` (estimates, the reads and their caps), `test_prusalink_jobs.py` (the lifecycle and reconnects), `test_prusalink_adapter.py` (config, `check()`, `run`, poll timing, and the whole bridge against the fake API).

## The OctoPrint adapter

`adapters/octoprint/` watches a printer run by OctoPrint. **It is checked against a real OctoPrint** (1.11.8 with its virtual printer, October 2026): `tests/fixtures/octoprint/` holds its answers and socket messages through a completed and a cancelled print, recorded with `tests/integration/record_octoprint.py`, and `tests/integration/test_real_octoprint.py` (`pytest -m integration`, with `OCTOPRINT_URL` and `OCTOPRINT_API_KEY` naming such an OctoPrint) compares `tests/fake_octoprint.py` with it and runs the adapter against it. The test takes an OctoPrint you start (its docstring has the commands for one in a virtual environment; Docker's `octoprint/octoprint` image works too) rather than starting one itself as the Moonraker tests do.

- **`client.py`**: aiohttp, `X-Api-Key` on every request; 403 (or 401) is `Refused`. `POST /api/login` with `{"passive": true}` gives the key's user and a session; the socket is SockJS's raw WebSocket, `/sockjs/websocket`, one JSON message per frame, which sends `connected` and then nothing about printing until `{"auth": "<user>:<session>"}`. A trace keeps the login's answer without its session, and of `/api/settings` (every plugin's settings, which can hold a Discord webhook's token or the Webhooks plugin's headers) only the webcam's snapshot fields and whether a webhook posts to 3D Print Log. Of the socket it keeps in full only the messages the bridge reads (`connected`, `current`, `history`, `event`, `reauthRequired`); of any other, such as a plugin's `plugin` message, only its type and the plugin's name.
- **`adapter.py`**: config (`url` with an optional port and path, `api_key`, `files`, `snapshots`), then per connect `/api/version` (`server` is the host software, `OctoPrint`; OctoPrint doesn't say which firmware the printer runs), `/api/settings` (the snapshot URL, `webcam.snapshotUrl` or a 1.9+ webcam's `compat.snapshot`, a loopback host taken as OctoPrint's; and `webhooks.py`), the login, and the socket with `{"throttle": 4}` (a `current` every 2 s). Messages go through a queue to the tracker, so a file read doesn't hold up the socket and its heartbeat. Backoff 5 s doubling to 60 s; 5 minutes after a refused key. `check()` asks `/api/version`, the login, `/api/printer` (409: OctoPrint isn't connected to the printer, a warning) and the settings.
- **`jobs.py`**: `history` (once, after `auth`) and `current` carry `state.flags`, `job`, `progress` (`completion` and `filepos` by bytes, `printTime` without time paused), `serverTime` and `markings`, the print chart's marks (`print` at a start, `done`, `cancel`, `pause`, `resume`, `connected`, epoch times). OctoPrint keeps marks for `temperature.cutoff` only (30 minutes): each new mark drops the older ones (`printer/standard.py`, `DataHistory`), so a long print's start mark is gone at its next pause or at its end. So **a job's identity is fixed once**, when a status first shows a file `printing`, `paused`, `pausing` or `resuming` (never `finishing` or `cancelling`, nor in state `Starting`: `printing` is already true then, but the `print` mark comes later, with `PrintStarted`): `started_at` is the latest `print` mark not followed by a `done` or `cancel` (one that is belongs to the last print), else `serverTime` less `printTime`, and `job_id` is `<epoch>-<stem>`. It stays that job while statuses show the same path under way, paused or on its way out; a `print` mark after its start, another path, or `filepos` going back is another job (`printTime` can't tell: it drops at each resume by the time paused). The path, last progress, `filepos` and the G-code's byte span are kept beside `CurrentJob` (`state.discovery["octoprint_job"]`), so a reconnect or a bridge restart finds the job by its path, never by recomputed times. After an end, a status for the same file starts nothing until `PrintStarted` or a newer `print` mark (a status still `printing` comes after `PrintDone`). It ends at `PrintDone` (completed), `PrintCancelled`, or `PrintFailed` (`reason` `cancelled`, else failed with the last `Error` event's text in the note); OctoPrint sends `PrintFailed` after `PrintCancelled` too, which finds no job. The end is when the event comes, on OctoPrint's clock, not the start plus the event's `time`, which leaves out the time paused. A job gone without its event (after a reconnect or a restart, or OctoPrint restarted under it) is ended by the first `done` or `cancel` mark after its start and after the bridge first saw it (an earlier one is the last print's), at that mark's time, else failed when OctoPrint is in error (`flags.error`, or a state with "Error" in it) or an `Error` event came, else by the last progress kept: completed at 99% or more, cancelled below, with a note. A job not completed is charged its estimate times the share of its G-code sent (`filepos` between the end of the header and thumbnails and the start of the settings block, from the two reads below), else times `completion`. `closedOrError` alone isn't an error: OctoPrint says it whenever it has no printer connection, as after its own restart (state `Offline`). Times are on OctoPrint's clock: the bridge's is offset by the difference in the last status.
- **`files.py`**: `/api/job`'s analysis (`estimatedPrintTime`, `filament.tool<N>.length` in mm; `volume` is unused, having no density) for every file; for a `local` one, two `Range` reads of `/downloads/files/local/<path>` (OctoPrint answers 206), the first 256 KB (the header and embedded `; thumbnail begin` PNG/JPG blocks, the largest kept, QOI skipped, and where the G-code starts) and the last 512 KB (the settings block: `filament used [g]` and `[mm]` per tool, preferred to the analysis, `printer_model`, the slicer summary, and where the G-code ends), else the PrusaSlicer Thumbnails plugin's `thumbnail`. What it reads of the settings is `adapters/common/slicer_meta.py`, shared with PrusaLink.
- **`webhooks.py`**: the OctoPrint-Webhooks plugin (`plugins.webhooks`: `hooks` in version 3, a single `url` before) with an enabled hook to 3dprintlog.com or a host under it is the `webhook` warning, as `notifier.py` does for Moonraker. The bridge's prints (`externalSource` `octoprint`) and the webhook's (`octoprint-webhook`) have different ids, so until the API drops webhook events for a printer with a live `octoprint` bridge connection, as it does for Moonraker's notifier (api#150), both log the print.
- **`discovery.py`**: `_octoprint._tcp` answers with OctoPrint's own TXT keys, `api` and `version` (`adapters/common/mdns.py`), or with no TXT at all (it can come in another packet) and a name without "PrusaLink", with `vendor` and `model` as the model and `uuid` as the serial; the record's `u` and `p` (a basic auth user and password) are never kept. PrusaLink on a Pi answers to `_octoprint._tcp` too, as "PrusaLink at <host>" with only `path` (Prusa-Link's `service_discovery.py`), so OctoPi on a Prusa MK3S is OctoPrint and PrusaLink is PrusaLink. Both PrusaLink kinds also register `_prusalink._tcp` (Buddy's `lib/WUI/mdns/mdns.c`), which the PrusaLink hook now asks for beside the `_prusa-link._tcp` it asked for before. Nothing is asked of OctoPrint.

Still to do (#83): timelapse videos (`/api/timelapse`), an application-key flow (the AppKeys plugin) instead of a pasted key, spools from the SpoolManager or FilamentManager plugins, and the API-side dedupe above. Tests: `tests/test_octoprint_adapter.py`.

## The SDCP adapter

`adapters/sdcp/` watches an Elegoo Centauri Carbon over SDCP v3. **It is built from documentation, not from a recorded printer** (#94): the protocol's published description (cbd-tech, `SDCP-Smart-Device-Control-Protocol-V3.0.0`, which has no license, so it is described in our own words and nothing is copied), Elegoo's own client library (elegooofficial/elegoo-link, Apache-2.0, `src/lan/adapters/elegoo_fdm_cc/`), the printer's firmware source (elegooofficial/CentauriCarbon, GPL-3.0, `print_stats_c.h`, read for facts only), and community notes recorded from a printer (WalkerFrederick/sdcp-centauri-carbon, firmware 1.1.29; danielcherubini/elegoo-homeassistant). `tests/fake_elegoo.py` follows the same sources. `protocol.py` marks every point not confirmed by them with ASSUMPTION; replace the fake's messages with a real trace (`trace = true`) when one exists, and check each.

- **`protocol.py`**: discovery (`M99999` to UDP 3000), the websocket (`ws://<host>:3030/websocket`, no authentication, `ping`/`pong`), the request shape, the only two commands the bridge sends (Cmd 0, the status again; Cmd 1, the attributes; `request()` refuses any other), and the Centauri Carbon's print states (`PrintInfo.Status`: 13 printing, 5 pausing, 6 paused, 12 resuming, 7 stopping, 8 stopped, 9 complete, 14 error, and the start routine's 1 and 15 to 22), which the firmware and elegoo-link agree on and the resin spec doesn't.

The mainboard id from the printer's messages is kept in `state.discovery["sdcp_mainboard_id"]` for the requests' `MainboardID` and `Topic` (empty until known) and for `watches`. Firmware `Elegoo` and the attributes' `FirmwareVersion`; no host software. Backoff 5 s doubling to 60 s. `check()` and `printer_details()` ask for the attributes on a connection of their own. A trace keeps status pushes, the acknowledgements of Cmd 0 and 1 and `pong` in full, of the attributes only `TRACED_ATTRIBUTES` (they also name the Wi-Fi network and the MAC address), and of anything else only its kind.
- **`jobs.py`**: pushes are merged into one status (`PrintInfo` field by field, in case a push carries only what changed; reset on each connect). A job starts only at a print state under way (13, 5, 6, 12) with a file: never in the start routine, which may still show the last job's file and task. Its identity is fixed then: `started_at` is the status's `TimeStamp` (the printer's clock, used when it is after 2020) less `CurrentTicks` (seconds on this printer), `job_id` is `<epoch>-<stem>`, and its path, `TaskId`, progress, layer and first sight are kept beside `CurrentJob` (`state.discovery["sdcp_job"]`). It stays that job while statuses show the same file and no other task, under way or busy (the start routine again on a resume, a filament change, stopping), unless layer and progress go back while printing (another print of the same file). It ends live at 9, 8 or 14 (an end naming no file or task is this job's: the file name is reported cleared after a cancel) at the status's time. After a connect, an end state for this job says how it ended (at the time last seen); anything else ends it by the progress kept (99% complete, else cancelled, with a note), an idle printer after a restart included. After an end, a status still showing that job printing starts nothing until the printer moves on. Usage is the file's estimate (`files.py`) scaled by progress for a job that didn't complete, marked estimated; the file's thumbnail and header go out with the start.
- **`files.py`**: one ranged GET of the first 256 KB of `http://<host>:<http_port>/downloadFile<path>` (port 80; a bare file name is under `/local`; `..` refused; no redirects; 15 s, since the websocket waits meanwhile). ASSUMPTION: the endpoint is reported only by bjan/pycentauri's `docs/PROTOCOL.md`. It reads Elegoo Slicer's (OrcaSlicer's) header, `; total filament weight [g] : ...`, `; total filament length [mm] : ...` (comma separated per tool) and `total estimated time`, plus PrusaSlicer's `filament used [g] =`, and the largest PNG/JPEG thumbnail (`common/slicer_meta.thumbnail_from`). Any failure is an empty `JobFile`.
- **`discovery.py`**: `ask()` sends `M99999` from an unbound socket (the first send gives it an ephemeral port; the answers come back there) and reads answers for 3 s, once per mainboard id; `SdcpDiscovery.sweep` asks each scanned network's broadcast address and 255.255.255.255, and reports `Found("sdcp", <address>, 3030, model, name, mainboard_id=...)`. A printer never announces itself unasked, so only a scan finds one. `printlog-bridge discover` asks too (`--no-sdcp` skips it) and prints a `[printer]` section for each address.

To check on a real printer: whether a push carries the whole status or only what changed; that `CurrentTicks` and `TotalTicks` are seconds and `TimeStamp` is epoch seconds; that `TaskId` is one per print and stays through pauses and a power-loss resume; which states a print passes through from start to end on each firmware, and whether an end state stays until the next print; whether `Filename` is cleared after a cancel; whether an empty `MainboardID` in a request is accepted; how long the printer keeps a silent client, and whether a second client (Elegoo Slicer, the app) beside the bridge is fine; whether `GET /downloadFile/local/<file>` on port 80 serves the file and honors `Range`, and whether Elegoo Slicer's header has the estimates `files.py` reads; whether Cmd 320/321 (history) are worth using; and what the camera serves. Elegoo's resin printers speak SDCP v3 over the same websocket, but with the spec's resin print states and ticks in milliseconds: one adapter could cover them with a state table per kind (resin is #97). The Centauri Carbon 2 speaks MQTT instead. Tests: `tests/test_sdcp_jobs.py` (the lifecycle, pauses, reconnects, restarts, missed ends), `tests/test_sdcp_adapter.py` (config, `check()`, `run`, pings, the trace, discovery, `discover`, and the whole bridge against the fake API), `tests/test_sdcp_files.py` (the header, the download path, the ranged read, failures, and the estimate reaching the fake API marked estimated).

## The Duet adapter

`adapters/duet/` watches a Duet board running RepRapFirmware, standalone (Duet 2 and 3) or with an SBC (a Duet 3 with DuetSoftwareFramework on a Raspberry Pi). **It is built from documentation, not from a recorded board** (#89): Duet3D's "RepRapFirmware HTTP requests" and "Object Model" pages, DuetWebControl's `PollConnector`/`RestConnector` and its object model classes, DuetSoftwareFramework's `MachineController`, and RepRapFirmware's mDNS code. `tests/fake_duet.py` follows the same sources. Each module marks its assumptions; replace the fake's answers with a real trace (`trace = true`) when one exists, and check each point below against it.

- **`client.py`**: aiohttp, GET only. Standalone: `rr_connect?password=` (RRF's default `reprap` when none is configured, since a board without M551 takes any; never `time=`), whose `sessionKey` (RRF 3.5+) goes in `X-Session-Key`; `err` 1 is `Refused`, 2 (no free session) and HTTP 503 are `Busy`. Between polls a cheap read of the live fields (`keep_alive`; `/machine/noop` with an SBC) runs every half `sessionTimeout`, so the session doesn't lapse between 30 s idle polls and `rr_connect` (the password, over plain HTTP) goes once per connection; it also cuts the wait short when `seqs.job` or `seqs.state` moved. A 401 (with an SBC also a 403) is a lapsed session anyway: it connects again, repeats the request once, and reads the whole model again. Error texts are scrubbed of the password (`safe_error`): aiohttp's name the request's URL. The model is read in full once per connect (`rr_model?key=<k>&flags=d99vn` for `boards`, `job`, `move`, `network`, `sbc`, `state`, `tools`, with `next`/`a<n>` paging for arrays), then each poll reads `rr_model?flags=d99fn` and again in full each key whose `seqs` moved, merged into one model (`model.merge`). `rr_fileinfo` and `rr_thumbnail` (base64 a piece at a time, following `next`) for files; `rr_disconnect` on stop, bounded by 2 s. When `rr_connect` is 404 it is SBC mode: `/machine/connect`, `/machine/model` (`/machine/status` before DSF 3.4) at each poll, `/machine/fileinfo/<file>?readThumbnailContent=true`, `/machine/disconnect`. DSF's websocket isn't used, so both modes share one tracker. A trace keeps request paths and parameters without the password, answers without the session key, and of the model only `TRACED_KEYS` and `network.name`.
- **`model.py`**: what is read of the object model (its docstring lists the fields). `slots_of` maps each extruder to the lowest-numbered tool that drives it (`tools[].extruders`), else its own index, so a toolchanger whose T0 drives extruder 2 reports extruder 2's feed on slot 0.
- **`jobs.py`**: a job starts at the first poll showing `job.file.fileName` with the board `processing`, `pausing`, `paused` or `resuming` (never `simulating`), with `started_at` now less `job.duration` and `job.pauseDuration`, and `job_id` `<epoch>-<stem>`. While connected it carries on through `UNDER_WAY` states as long as the file is the same and `job.duration` hasn't gone back, never judged by the wall clock; `disconnected`, `starting` and `updating` change nothing; it ends when the file is gone or the board idle (cancelled by `lastFileCancelled`, failed by `lastFileAborted`, else completed), or at once on `halted` or a lower `state.upTime` (the board restarted). Usage is `move.extruders[].rawPosition` (reset when a print starts, so a restart mid-print loses nothing), each poll's gain times the `factor` of that moment, by slot, sent as `filament_mm` with `usage_estimated` off; else `job.rawExtrusion` the same way (split by the slicer's share on several tools); else the slicer's estimate scaled by `filePosition`, estimated. The slicer's figures are per tool. A mixing hotend's extruders are summed into its tool's slot (a follow-up). `CurrentJob` keeps the running job, its file, what it fed and the board's `upTime` in `state.discovery["duet_job"]`; after a bridge restart the same file with a start within `SAME_START_S` (300 s), or paused, is the same job, a lower `upTime` fails it with what was kept, and a remembered job whose file is the board's `lastFileName` ended as its flags say, measured, at its start plus `lastDuration`.
- **`files.py`**: the board's own reading of the file (`filament` mm per tool, `printTime`, `generatedBy`, `layerHeight`, `thumbnails`); no grams. The thumbnail is the largest PNG or JPEG, read only when the sink asks.
- **`discovery.py`**: `_http._tcp` answers whose TXT `product` names RepRapFirmware or a Duet (`LwipEthernetInterface.cpp`); nothing is asked. `printlog-bridge discover` asks too (`--no-duet` skips it). A Duet on Wi-Fi or behind an SBC may send no such TXT.

To check on a real board: `rr_connect`'s answer on RRF 3.4 and 3.5 (session keys, `isEmulated` on DSF), whether an expired session answers 401, which fields `flags=f` carries (the tracker reads `state.status`, `job.duration`, `job.filePosition`, `job.rawExtrusion` and `rawPosition` from it, and `seqs` for the rest), whether `rawPosition` is reset at a print's start and kept after its end, and whether it counts retractions and a filament change's unload and load; `job.duration` with pauses; `lastFileName`, `lastFileCancelled` and `lastFileAborted` after a cancel, an abort and an M112; `job.file` between jobs (null, or `fileName` null); `rr_fileinfo`'s thumbnail fields and `rr_thumbnail`'s `next`; DSF's `/machine/model` vs `/machine/status`, `/machine/noop`, its session timeout and its fileinfo thumbnails; whether `state.upTime` is in the live fields; and the mDNS TXT on Ethernet, Wi-Fi and SBC boards. Tests: `tests/test_duet_jobs.py` (the lifecycle, toolchangers, restarts, missed ends, fallbacks), `tests/test_duet_adapter.py` (config, `check()`, the client, `run` standalone and SBC, the trace, discovery, `discover`, and the whole bridge against the fake API).

## The Anycubic adapter

`adapters/anycubic/` watches an Anycubic printer in LAN mode: the Kobra S1 and Kobra 3 (FDM) and the Photon P1 and P1 Max (resin), which share one protocol. **The handshake, the topics and the idle reports are checked against real printers** (a Kobra S1 on firmware 2.5.6.4 and a Photon P1 Max, October 2026, `tests/fixtures/anycubic/`, recorded with `tests/integration/record_anycubic.py`, which also redacts a recording for the fixtures); **the job fields and states are not** (no print recorded yet): they come from Nino6689/anycubic-lan's `docs/PROTOCOL.md` (MIT) for FDM and modrzew/hass-anycubic-photon-p1's `docs/protocol.md` (MIT) for resin, with rvanderp3/kobra-connect (Apache-2.0) for the handshake. No code of theirs is used; GPL projects (hass-anycubic_cloud) weren't read. `jobs.py` marks each point taken from them with ASSUMPTION. `tests/fake_anycubic.py` serves the recorded answers and builds the job reports from those sources.

- **`handshake.py`, `aes.py`**: `GET /info` on port 18910 (`ctrlType` `lan` or `net` is LAN mode; `cloud` is `LanModeOff`), then `POST /ctrl?ts=<ms>&nonce=<n>&sign=<md5(md5(token[:16]) + ts + nonce)>&did=<any>`. Its `data.info` is AES-128-CBC, key `token[16:]`, IV `data.token`; the plaintext is JSON padded with PKCS#7 (the S1) or with the padding byte's value too on the P1 Max (the doc says zeros: the JSON is cut at its end either way). It holds `broker` (`mqtts://<ip>:9883` on the S1, `<ip>:8883` on the P1 Max), `username`, `password`, `deviceId` (32 hex characters on the S1, 28 on the P1 Max), and `clientId` on the P1 (the literal `clientId`, which the broker insists on); the S1 adds `devicecrt` and `devicepk`, which the broker doesn't ask for, and the P1 `fileUploadUrl` and `mac`. AES is pure Python (`aes.py`), since the bridge runs without `cryptography`. The S1 answers `/ctrl` chunked. A fresh handshake on every connect: the token changes on every `/info`.
- **`protocol.py`**: reports on `anycubic/anycubicCloud/v1/printer/public/<modelId>/<deviceId>/<type>/report`, acknowledgements (`{"msgid"}`) on `.../response`; requests on `anycubic/anycubicCloud/v1/web/printer/<modelId>/<deviceId>/<type>` (FDM) or `/pc/` (resin, as Photon Workshop). `READ_ONLY` is every (type, action) the bridge may send, and `Topics.request` refuses anything else. TLS without verification and with `SECLEVEL=0` (the P1's certificate is RSA 1024 with SHA-1).
- **`adapter.py`**: config (`host`, `port` 18910, `mqtt_port` to override `/ctrl`'s), one handshake and MQTT connection per connect, always to `host`. A task sends the queries on connect and every `query_s` (30 s); the read loop waits on it beside the pending receive, so a query that fails ends the session at once. A Photon's broker takes only `/ctrl`'s client id, so a session of a resin printer that ends within `takeover_s` (30 s) was taken over by another client (Photon Workshop): the bridge waits `takeover_backoff_s` (5 minutes) before the next handshake, with one warning (`takeover`) until a session lasts. A trace drops `urls`, IP and MAC addresses, the serial (`cn`, `sn`), device and client ids and anything naming the Wi-Fi network, at any depth. The serial and model id go in `state.discovery["anycubic_identity"]` for `watches`. Firmware is `Anycubic` and `info`'s `data.version` (FDM) or `lanInfo`'s (resin, ASSUMPTION: `firmware_version`); no host software. Backoff 5 s doubling to 60 s; LAN mode off is a warning, retried every minute. `check()` and `printer_details()` do the handshake, connect and wait for the first answer.
- **`jobs.py`**: the job is `info`'s `data.project` (FDM; null between jobs) and the `print` report's `data` (merged in), or on resin only the `print` report, its envelope `state` the job's, with `status` `idle` clearing it. A `print` report without a file (only part of the job, as can come first after a reconnect or a restart) decides nothing until a report names the file. On resin, `idle` with the job at its last layer (or 99%) ends it completed; short of that, it waits for the job's own `print` report until the next status, then ends by progress at when it went idle. A job starts at `printing`, `paused`, `pausing`, `resuming` or `resumed` with a file (never the start routine), with `started_at` now less `print_time` (ASSUMPTION: minutes) and `job_id` `<epoch>-<stem>`; it is kept with its file, task id, progress, layers and usage beside `CurrentJob` (`state.discovery["anycubic_job"]`). It ends at `finished`, `stoped`/`stopped`/`canceled` or `failed` (or `print_status` 2 or 3); gone without an end, `last_project` decides when it names the job, else the progress kept (99%). Usage: FDM `supplies_usage` (ASSUMPTION: mm fed so far) as slot 0's millimeters, marked estimated; resin `supplies_usage` (the job's mL) as `estimated_volume_ml` and, at the end, all of it for a completed job, else by layers printed.
- **`discovery.py`**: an SSDP M-SEARCH for `ac:3dprinter:fdm` and `ac:3dprinter:lcd` to 239.255.255.250 and each network's broadcast from an ephemeral port, in a scan and in `discover` (`--no-anycubic` skips it). Both printers answered with `ST`, `USN: uuid:<fdm|lcd>:<MAC>` and a `LOCATION` with `/info`'s fields as its query, the token included (dropped). Neither announced itself in three minutes of listening.

To check with a recorded print (`python tests/integration/record_anycubic.py <ip> <raw dir> --seconds <print length + 60>`, then `--redact` into `tests/fixtures/anycubic/`): the job states from start to end, including a cancel and a failure; whether `print_time` and `remain_time` are minutes; whether `supplies_usage` is mm fed so far or the slicer's total (then it should be scaled for a cancel); whether the printer pushes `info` or `print` reports on its own while printing; `last_project` after an end; `task_id` for a local start; the ACE Pro's `multiColorBox` slots and how a job maps to them; `file`/`fileDetails` for a thumbnail; the P1 Max's broker (closed in our shop, LAN mode on) and its `print` reports; and the Kobra 3. Tests: `tests/test_anycubic_handshake.py` (AES against FIPS-197 and `cryptography`), `tests/test_anycubic_adapter.py` (config, the handshake, `check()`, `run` for FDM and resin, reconnects, restarts, the trace, discovery, and the whole bridge against the fake API).

## The FlashForge adapter

`adapters/flashforge/` watches a FlashForge Adventurer 5M, 5M Pro or AD5X over the LAN HTTP API on port 8898 (firmware 2.x and newer on the 5M series, every AD5X). **It is built from community sources, not a recorded printer** (#88): GhostTypes/ff-5mp-api-py (MIT) and ff-5mp-hass (MIT), and the facts only of ff-5mp-api-ts (no license file). Orca-Flashforge (AGPL) wraps a vendor library and says nothing of the protocol; no GPL code was used. `tests/fake_flashforge.py` follows the same sources. `protocol.py` and `jobs.py` mark each point not confirmed with ASSUMPTION.

- **`protocol.py`**: every request is a `POST` with `{"serialNumber", "checkCode"}`, answered `{"code": 0, "message": "Success", ...}`; another `code` is a refused serial or check code. `READ_ONLY` is `/detail`, `/product`, `/gcodeList` and `/gcodeThumb`; the client refuses anything else (`/control`, `/printGcode`, `/uploadGcode` change the printer). `view_of` reads `/detail`: `status` (`printing`, `pausing`, `paused`, `pause` under way; `busy`, `heating`, `calibrate_doing`, `downloading` busy; `completed`, `cancel`, `error` ends; `ready`), `printFileName`, `printProgress` (0 to 1), `printDuration` (seconds), `estimatedTime` (seconds left), `printLayer`/`targetPrintLayer`, `estimatedRightWeight` (grams) and `estimatedRightLen` (mm), `errorCode`, `firmwareVersion`, `pid` (35 5M, 36 5M Pro, 38 AD5X) and the IFS, `matlStationInfo.slotInfos` (`slotId` 1 to 4 is slot 0 to 3, `hasFilament`, `materialName`, `materialColor`). `filament_by_slot` reads an AD5X's `/gcodeList` `gcodeListDetail[].gcodeToolDatas` (`slotId`, `filamentWeight`) for the job's file.
- **The legacy TCP port 8899** (`~M115`, `~M119`, `~M27`) isn't used: every source sends `~M601 S1` (take control) first, which would push FlashPrint or Orca off, and none says whether the reads work without it. `check()` connects to it (sending nothing) only when the HTTP API doesn't answer, to say the firmware is too old; it also asks Moonraker's `/server/info` on 7125, to point Klipper Mod, Forge-X and ZMOD owners at `adapter = moonraker`.
- **`client.py`**: aiohttp, 10 s per request, at most 4 MB per answer. A trace keeps the path (never the body) and of `/detail` only `TRACED_DETAIL`.
- **`adapter.py`**: config (`host`, `serial`, `check_code` used as given, `port` 8898, `poll_interval` 5 s, `idle_poll_interval` 30 s, `files`), one `/detail` per poll. Firmware `FlashForge` and `firmwareVersion`; no host software. Backoff 5 s doubling to 60 s; 5 minutes after a refused check code (`credentials_refused(("check_code",))`). `app_options` needs the serial from the app (a found printer carries it) and the sealed `check_code`. `watches` by serial, else address and port. `use_spools` passes the AD5X's slots on as `SpoolReading`s (material and color, no tag) when they change.
- **`jobs.py`**: a job starts at the first status under way with a file, with `started_at` now less `printDuration` and `job_id` `<epoch>-<stem>`; it is kept with its file, progress, duration and estimates beside `CurrentJob` (`state.discovery["flashforge_job"]`). It carries on through busy states (heating may show no file) while the file is the same and the duration hasn't gone back (another print of that file), and ends at `completed`, `cancel` or `error` (one naming no file is this job's), at the poll's time; after a connect, an end state for its file says how (at when it was last seen), anything else ends it by progress (99%). **Usage is the printer's reading of the slicer's estimate** (`estimatedRightWeight` and `estimatedRightLen`, the largest seen), all of it for a completed job and times progress otherwise, `usage_estimated=True`; on an AD5X split by slot from `/gcodeList`. ASSUMPTION, from ff-5mp-api-py's code: these are the job's totals (it scales them by progress for "used so far"), not what is left. The job's file isn't downloaded: the API has no read-only way to.
- **`discovery.py`**: an empty datagram to 225.0.0.9 (ports 19000, 8899) and to the broadcast address (48899) from an ephemeral port, in a scan and in `discover` (`--no-flashforge` skips it). A 5M-series answer (276 bytes) has the name at 0, the product id at 0x88, the HTTP port at 0x8E and the serial at 0x92; an older printer's (140 bytes, no serial) is dropped.

To check on a real printer (`trace = true`): the answer to a wrong check code (its `code` and `message`), and to a wrong serial; every `status` from start to end, through a pause, a filament runout, a cancel and an error, and whether `completed`/`cancel` stay until dismissed, with `printFileName` and `printProgress` kept; whether `printProgress` is 0 to 1; whether `printDuration` counts pauses; whether `estimatedRightWeight` and `estimatedRightLen` are the job's totals from the start, and on an AD5X multicolor print whether they cover every slot; `gcodeListDetail` on an AD5X (slots, grams) and on a 5M (absent?); `/gcodeThumb` for the running file; the discovery answer's layout and whether the printer answers an empty datagram; `/detail` on the 5M Pro and on 5M firmware below 2.x (404?); whether 8898 stays up on the Klipper Mod, Forge-X and ZMOD. Tests: `tests/test_flashforge_jobs.py` (the view, the lifecycle, restarts, the AD5X slots), `tests/test_flashforge_adapter.py` (config, `check()`, `run`, the trace, discovery, `discover`, and the whole bridge against the fake API).
